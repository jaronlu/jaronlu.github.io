## 一、结论前置

1. **Coze（扣子）是字节跳动推出的 AI Agent 平台，国内版叫“扣子”（coze.cn），国际版叫 Coze（coze.com）。当前产品形态分两条主线：扣子是对话式的“AI 团队协作平台”（人 + 多 Agent 在项目里协作，Agent 靠技能、MCP、插件、长期记忆、工作台干活）；扣子编程（code.coze.cn）是一站式云端 Vibe Coding 平台，用对话生成智能体、工作流、网页、App、小程序并一键部署。原来的“低代码开发平台”是扣子编程的旧版，官方已不再向新注册用户开放，存量用户可从扣子编程首页“回到旧版”进入。**

2. **扩展 Agent 能力的是三样东西，不是一堆插件——技能（Skill，封装“怎么干”的步骤与经验）、MCP（连接外部工具与数据）、插件（把技能、MCP 和可选的 Panel 工作界面打包成可安装的能力）。再配上编排（工作流）、知识（知识库）、记忆（变量/数据库/记忆库）、自动化（触发器），才构成一个能交付结果的 Agent。2026 年 1 月的“扣子 2.0”发布时，这套能力叫 Agent Skills 与 Agent Plan；今天的官方叫法是“技能商店/技能包”与“长期任务”。**

3. **Coze vs Dify 的核心区别：Coze 是“零代码优先 + 分发优先”（不写代码就能做出应用，发布到抖音小程序、飞书、微信等渠道），Dify 是“开发者优先 + 数据控制优先”（开源可自托管，RAG 引擎和模型管理更强，适合需要深度定制和数据控制的企业）**。Coze 商业版是云服务，数据在平台上；它另有一个开源版 Coze Studio（Apache-2.0，Go 后端 + React 前端，Docker 自托管），但社区版更新明显滞后于商业版、部分能力缺失，不能等同于“Coze 可以完全自托管”。**两者的定位不同：非技术用户与运营团队选 Coze，需要深度定制和数据控制的开发者/企业选 Dify 或代码框架。**

## 二、通俗类比 + 专业定义

### 通俗类比

#### 扣子 = AI Agent 的“一站式开店平台”

- **扣子平台 = 商业地产（万达广场）**：
  - 你想开店（做一个能交付结果的 Agent），不需要自己买地盖房（写代码搭后端、接模型、搭 RAG）
  - 万达广场（扣子平台）提供现成的商铺（智能体框架）、水电（模型与集成服务）、装修工具（对话生成 + 可视化编排）
  - 你只需要“装修”（配人设、装技能、接 MCP、挂知识库），就能“开店”（发布到渠道）
  - 而且万达广场自带客流（飞书/微信/抖音小程序等发布渠道），你的店一开就有潜在顾客
  - 想自己盖楼也行——扣子编程给你云端沙箱、集成服务和一键部署，但施工质量还是看你自己的需求复杂度

- **Bot 人设和提示词 = 店铺的“招牌和服务规范”**：
  - 你给 Bot 起名字、设头像、写“人设”（System Prompt）——就像给店铺起名字、设计招牌、制定服务规范
  - 例如：“你是一个专业的旅游顾问，热情、耐心、熟悉深圳周边景点，回答要具体实用”——就像店铺的服务标准
  - 人设决定了 Bot 的“性格”和“服务方式”

- **插件（Plugin）= 店铺的“设备和供应商”**：
  - 开店需要设备（如餐厅需要灶台、冰箱）和供应商（如食材供应商）
  - 扣子的插件是 Agent 的“设备和供应商”——一个插件可以把技能（怎么做）、MCP（连什么）和可选的 Panel 工作界面（在哪儿干）打包在一起
  - 插件商店按场景分类（资讯阅读、旅游出行、效率办公、图片理解等）；官方插件和三方插件都分免费与付费，付费按调用量（次数、时长）计费
  - 在扣子编程（低代码那一侧），“插件”指的是工具集：一个插件含一个或多个工具（API），同一个插件内的工具必须同域名
  - 你也可以“自定义设备”——基于已有服务创建、导入 OpenAPI/Swagger、基于 MCP 服务创建，或在扣子编程里让 AI 帮你写

- **工作流（Workflow）= 店铺的“操作流程 SOP”**：
  - 复杂的店铺有标准操作流程（SOP）——顾客进店→迎宾→点单→制作→出餐→结账
  - Coze 的工作流就是 Bot 的“SOP”——用可视化拖拽的方式定义多步骤处理流程
  - 每个步骤是一个“节点”（LLM 调用、插件调用、知识检索、条件判断、代码执行）
  - 节点之间用线连接，定义执行顺序和数据传递
  - 适合复杂的、多步骤的任务（如“生成一份市场分析报告”：收集数据→分析数据→生成大纲→撰写报告→审查）

- **知识库（Knowledge Base）= 店铺的“内部资料库”**：
  - 店铺有内部资料（产品手册、FAQ、操作指南），员工遇到问题可以查
  - Coze 的知识库就是 Bot 的“内部资料库”——你上传文档（PDF/Word/表格/网页），Bot 回答问题时会先查知识库
  - 这就是 RAG（检索增强生成）——基于你的文档回答，减少“胡说八道”（幻觉）
  - 例如：你上传了“产品说明书”，用户问“这个产品怎么用”，Bot 会先查说明书，然后基于说明书回答
  - 知识库分两类：扣子知识库（文本/表格/图片三种形态）与火山知识库（结构化/非结构化），官方建议生产环境用火山知识库

- **记忆（Memory）= 店铺的“顾客档案”**：
  - 高级店铺会记录老顾客的偏好（如“张总喜欢靠窗的位置”、“李女士不吃辣”）
  - 扣子的记忆能力分三层：变量（存语言偏好、会员等级等固定字段）、数据库（存结构化业务数据）、记忆库（长期记忆，自动从对话里提取用户画像与关键事件）
  - 官方对知识与记忆的划界很清楚：知识是开发者维护、所有用户可见不可改、可跨智能体共用的静态数据；记忆是终端用户使用时产生的动态数据，不能跨智能体使用
  - 记忆库有按套餐分级的条数上限，触顶后本次写入失败，只能删旧数据或升级套餐

- **技能（Skill，扣子 2.0 时叫 Agent Skills）= 店铺的“专业服务套餐”**：
  - 有些店铺提供“专业服务套餐”（如理发店的“烫染套餐”、餐厅的“商务套餐”）
  - 技能就是把“场景最佳实践 + 所需工具”封装成可安装的模块：特定任务的步骤、经验和判断，Agent 判断当前任务相关就自动加载
  - 例如“A 股投资分析技能包”会组合板块热度分析、量化股票分析、实时股票数据查询等技能
  - 技能有三类来源：官方技能、三方技能（商店里，部分收费）、自定义技能（自己沉淀或让扣子编程生成）
  - 技能通过“渐进式披露”加载：Agent 先只读技能的介绍信息，判定相关才装入详细内容，省上下文窗口

- **长期任务（扣子 2.0 时叫 Agent Plan）= 店铺的“长期项目执行”**：
  - 传统的 Bot 是“顾客问一句，店员答一句”（单次响应）
  - 长期任务是“长期项目执行”——你定目标、定完成方式，Agent 自己分解步骤、持续执行、主动汇报，直到交付
  - 例如：“帮我研究一下 AI Agent 行业，一周后给我一份完整的行业分析报告”——Agent 会把宏观目标拆成多步，管理中间状态，持续推进
  - 这让 Bot 从“聊天机器人”升级为“可持续运作的智能体”；官方 2.0 发布会把这套能力归为 Agent Plan（长期计划）

- **发布渠道 = 店铺的“销售渠道”**：
  - 店铺开好后，需要销售渠道才能卖东西（实体店、外卖平台、电商平台）
  - 扣子的发布渠道就是“销售渠道”——一次开发，多端运行
  - **国内版（扣子）渠道**：
    - 扣子商店（智能体/应用商店，用户可以发现和使用）
    - 飞书（含飞书多维表格）
    - 微信客服、微信服务号、微信订阅号
    - 抖音小程序、微信小程序
    - 掘金（评论区 @ 调用）
    - API、Chat SDK（网页悬浮窗）
    - 团队自定义渠道 / 公共渠道（渠道商入驻后可用）
  - **国际版（Coze）渠道**：
    - Coze Store、Discord、Telegram、Slack、Messenger、LINE、WhatsApp、API、托管网页
  - 注意：渠道清单会变，以官方“了解项目发布”页为准；旧资料里的“豆包渠道”在当前官方渠道表中已不存在
  - 多渠道发布是 Coze 的核心优势——一次开发，多端运行

- **订阅套餐 = 店铺的“租金和服务费”**：
  - 免费版 = “免费摊位”——基础功能，额度最小的存储与记忆
  - 个人进阶/高阶/旗舰/尊享版 = “标准店铺逐级升级”——记忆条数、知识库空间、插件调用额度、云端 Agent 等能力逐档放开
  - 团队版/企业版 = “连锁店铺/旗舰店”——多人多空间、权限与访问控制、企业商店、公共渠道等
  - 除了订阅费，还要按用量付费：模型 Token、付费插件调用量、知识库存储、火山知识库的计算与存储，各项分开计费

### 二、两条构建路径

```
路径 A：低代码智能体（扣子编程旧版，存量账号可用）
1. 创建智能体
   ├── 名称、头像、人设与回复逻辑（System Prompt，上限 20000 字符）
   ├── 选择模型（豆包、DeepSeek、Kimi、GLM、MiniMax 等，随平台更新）
   └── 开场白、用户问题建议、快捷指令、语音、背景图
2. 装能力
   ├── 技能区：插件 / 工作流 / 知识库 / 记忆库
   ├── 触发器：定时或 Webhook 触发
   └── 变量、数据库、文件盒子
3. 调试
   ├── 预览区对话测试，看思考过程与工具调用
   └── 逐项调整提示词、插件、知识库召回参数
4. 发布
   ├── 选渠道（商店 / 飞书 / 微信 / 小程序 / API / Chat SDK）
   ├── 打包 → 扣子审核 → 渠道审核
   └── 看对话日志与反馈持续迭代

路径 B：扣子编程 / 扣子 Agent（当前主推）
1. 用自然语言描述目标（可上传材料、文档）
2. AI 判断需要哪些集成服务与技能，生成智能体、工作流、技能或应用
3. 在云端沙箱里预览、调试，逐步对话修改
4. 一键部署（默认域名或自定义域名），或把产物接回扣子 Agent 使用
```

### 三、插件系统

#### 插件分类（官方口径）
1. **资源库插件**：开发者自己在资源库中开发，仅当前账号可用，自行维护
2. **插件商店插件**
   - **官方插件**：扣子编程上架并维护，含免费与付费（按调用量计费，积分抵扣）
   - **三方插件**：开发者上架，含免费与付费；三方付费插件仅计费套餐用户可用，从现金账户扣费
3. **扣子侧的插件（能力包）**：一个插件可包含技能、MCP 与可选 Panel，安装到 Agent 后在对话中按意图调用

#### 自定义插件的四种创建方式（官方口径）
- 基于已有服务创建：填 API 信息，配置认证（API Key / OAuth / 无认证）
- 通过 JSON 或 YAML 导入：粘贴 OpenAPI/Swagger 规范
- 基于 MCP 服务创建：扣子编程内置 MCP 客户端，填 MCP 工具 URL 等配置即可把 MCP 工具变成插件
- 交给扣子编程生成：用对话描述需求，AI 写代码并调试

注意：同一插件内的不同工具必须使用相同域名；基于扣子付费插件封装的 MCP 工具，不能再二次封装成新插件。

#### 插件的结构
```
插件（扣子编程侧 / 工具集）
├── 基本信息（名称、描述、图标、分类）
├── 认证配置（API Key / OAuth / 无认证）
├── 工具列表（Tools）
│   ├── 工具 1（名称、描述、参数 Schema、API 端点）
│   ├── 工具 2
│   └── ...
└── 类型（HTTP / MCP）

插件（扣子侧 / 能力包）
├── 技能（完成任务所需的步骤与经验）
├── MCP（外部工具与数据连接）
└── Panel（可选，对话区右侧的可视化工作界面）
```

#### 插件的工作原理
```
用户提问 → 模型判断要不要调用工具（看工具名、描述、参数说明）
    ↓
选定工具 → 按 Schema 生成参数（可设默认值、可对模型隐藏）
    ↓
平台按插件配置注入鉴权（API Key / OAuth / 服务封装）→ 调用 HTTP API 或 MCP Server
    ↓
拿回结果 → 作为工具消息回到上下文
    ↓
模型基于工具结果组织回答
```

关键点：模型只“看见”工具的名称、描述与参数 Schema，看不见你的真实接口实现。所以描述写得含糊，模型就选错工具或填错参数——这也是插件描述比代码更值得打磨的原因。

### 四、工作流（Workflow）

#### 工作流的节点类型（按官方导入/导出规范的 type 取值归类）
| 节点类型 | 功能 | 示例 |
|---------|------|------|
| **开始 / 结束 / 输出** | 入口、出口与中间输出 | 定义输入输出变量 |
| **大模型节点** | 调用模型，可挂插件/工作流/知识库/记忆作为技能 | “总结这段文字并按三句话输出” |
| **插件节点 / 工作流节点** | 调用插件工具、调用已发布子工作流 | “调用搜索插件”“调用审批子流程” |
| **代码节点** | 执行 Python / JS 代码 | “算统计指标、清洗字段” |
| **意图识别 / 问答节点** | 分类路由；向用户追问并中断等待回复 | “判断是售后还是咨询” |
| **选择器（条件分支）** | 按条件走不同分支 | “VIP 走 A 路径，否则 B” |
| **循环 / 批处理节点** | 循环处理列表；批处理可并行跑一批数据 | “对列表每项执行同一流程” |
| **变量聚合 / 文本处理 / JSON 序列化** | 合并分支变量、字符串处理、JSON 编解码 | “把多个分支输出合并成一个变量” |
| **知识库检索 / 写入 / 删除** | 检索、写入、删除知识库文档 | “从产品知识库取片段” |
| **SQL 与增删改查节点** | 对指定数据表做 SQL 或图形化增删改查 | “查用户订单” |
| **长期记忆节点** | 写入与检索记忆库 | “记下用户偏好后下次召回” |
| **HTTP 请求节点** | 调用外部 API | “调用天气 API” |
| **图像 / 视频节点、消息节点、会话管理节点** | 生成图像视频、主动发消息、读写会话与历史 | “生成配图并推送” |

#### 工作流的执行流程
```
开始（输入变量）
    ↓
大模型节点（理解与改写）
    ↓
知识库检索节点
    ↓
选择器（条件分支）
    ├── 分支 A → 插件节点 → 变量聚合
    └── 分支 B → 代码节点 → 变量聚合
    ↓
结束节点（输出结果）
```

要点：分支必须汇合到变量聚合节点才能被下游引用；批处理节点可以让同一条子流程并行处理一批数据，但单个工作流内部没有 Dify 式的“并行节点”概念。

### 五、知识库（RAG）

#### 知识库的处理流程
```
文档上传（本地文件 / 在线网页 / Notion / 飞书文档 / 表格 / 图片）
    ↓
文档解析（提取文本、表格、图片标注）
    ↓
切分（自动分段，或自定义分隔符 / 最大分段长度 / 重叠）
    ↓
建索引（向量索引 + 全文索引；表格走索引列或 NL2SQL）
    ↓
检索（Query 改写 → 按策略召回：混合 / 语义 / 全文 → 可选 Rerank 重排）
    ↓
组装上下文（按最大召回数量取片段，连同匹配度一起给模型）
    ↓
模型生成回答（基于召回内容，而不是凭记忆编）
```

要点：扣子把“检索”做成节点级配置而不是全局开关——智能体里挂知识库是让模型自己判断要不要查，工作流里加知识库检索节点是强制查，两者的行为不一样。

#### 知识库的配置项（扣子知识库召回策略，官方字段）
- **搜索策略**：混合（全文 + 语义综合排序，默认推荐）/ 语义 / 全文（专有名词、缩写、ID 场景）
- **最大召回数量**：从知识库返回的最大段落数，默认 5
- **最小匹配度**：低于阈值的片段不召回，默认 0.5；**仅关闭结果重排时可设置**
- **结果重排**：用 Rerank 模型按相关性重排，适合客服、专业答疑等要高精度的场景
- **查询改写**：默认开启，按对话历史重写 Query；代价是多一轮模型调用
- **表格 SQL 查询**：加表格知识库后默认开启，自然语言转 SQL，结果与 RAG 片段一起给模型
- **仅查看个人文档**：限定只检索用户自己写入的文档，默认关闭
- **分块策略**：可选自动分段或自定义（分隔符、最大分段长度、重叠），建库后修改范围有限，先想清楚再建

#### 记忆的三层（易与知识库混淆）
- **变量**：Prompt 里引用的固定字段（用户名、等级），由开发者定义
- **数据库**：结构化数据表，支持自然语言增删改查，可开多用户模式
- **记忆库**：从对话中自动提取用户画像与关键事件；一个智能体只能绑定一个记忆库，一个记忆库可被多个智能体复用
- 划界：知识 = 开发者维护、可跨智能体共用的静态内容；记忆 = 终端用户产生的动态数据，不能跨智能体用

## 四、最小可运行代码

### 用扣子 OpenAPI 调智能体与工作流（完整 Python 客户端）

前置条件与环境变量：`pip install requests`，令牌和 ID 一律从环境变量读，不写进代码。

| 环境变量 | 用途 |
|---|---|
| `COZE_API_TOKEN` | 个人访问令牌（`pat_` 开头），扣子 → 账号设置 → 访问令牌 |
| `COZE_BOT_ID` | 智能体 ID，需已发布为 API 服务 |
| `COZE_WORKFLOW_ID` | 工作流 ID，可选，需已发布 |
| `COZE_BASE_URL` | 默认 `https://api.coze.cn`，国际版用 `https://api.coze.com` |

```python
"""
扣子 OpenAPI 最小可运行客户端（Python 3.10+，用了 `X | None` 类型语法）。

接口版本说明（与本文件对应的官方文档）：
  POST /v3/chat                     发起对话（流式 SSE），conversation_id 走 query 参数
  POST /v1/workflow/run             执行已发布工作流（非流式）
  POST /v1/conversation/message/list 查看会话消息，conversation_id 走 query，其余走 body
"""

import json
import os

import requests


class CozeClient:
    """只封装对话、工作流、消息列表三个最常用能力，便于读通协议。"""

    def __init__(self, token: str, base_url: str = "https://api.coze.cn"):
        self.base_url = base_url.rstrip("/")
        self.session = requests.Session()
        self.session.headers.update({
            "Authorization": f"Bearer {token}",
            "Content-Type": "application/json",
        })

    def chat(self, bot_id: str, user_id: str, query: str,
             conversation_id: str | None = None, timeout: int = 120):
        """发起一次对话并流式接收回复，返回 (answer, conversation_id, chat_id)。

        conversation_id 是 query 参数而不是 body 字段——这是 v3 与旧版 v1 最常见的踩坑点。
        """
        url = f"{self.base_url}/v3/chat"
        payload = {
            "bot_id": bot_id,
            "user_id": user_id,          # 仅用于数据隔离，不要传真实业务用户 ID
            "stream": True,
            "auto_save_history": True,   # 非流式时必须为 True，流式下保持默认开启
            "additional_messages": [
                {"role": "user", "type": "question",
                 "content": query, "content_type": "text"}
            ],
        }
        params = {"conversation_id": conversation_id} if conversation_id else None

        answer = ""
        conv_id = conversation_id
        chat_id = None

        # SSE 每个包是「event: 事件名」+「data: JSON」两行；事件名在 event 行，
        # 不在 data 里——很多示例写成 data["event"]，结果永远匹配不到，回包全空。
        with self.session.post(url, params=params, json=payload,
                               stream=True, timeout=timeout) as resp:
            resp.raise_for_status()
            event = None
            for raw in resp.iter_lines(decode_unicode=True):
                if not raw:
                    continue
                if raw.startswith("event:"):
                    event = raw[len("event:"):].strip()
                    continue
                if not raw.startswith("data:"):
                    continue
                data = raw[len("data:"):].strip()
                if data == "[DONE]":
                    break
                try:
                    obj = json.loads(data)
                except json.JSONDecodeError:
                    continue

                if event == "conversation.chat.created":
                    chat_id = obj.get("id")            # chat 事件里 id 即 Chat ID
                    conv_id = obj.get("conversation_id") or conv_id
                elif event == "conversation.message.delta":
                    # 只有 type=answer 的增量是正文；function_call、tool_response 属中间态
                    if obj.get("type") == "answer":
                        chunk = obj.get("content", "")
                        answer += chunk
                        print(chunk, end="", flush=True)
                elif event == "conversation.chat.failed":
                    raise RuntimeError(f"对话失败：{obj}")
                elif event == "done":
                    break

        print()
        return answer, conv_id, chat_id

    def run_workflow(self, workflow_id: str, parameters: dict,
                     bot_id: str | None = None, timeout: int = 600):
        """执行已发布的工作流（非流式）。

        坑：非流式接口 90 秒收不到响应就断开；含数据库/变量节点的工作流还必须传 bot_id。
        长任务改用 /v1/workflow/stream_run，或付费套餐传 is_async=True 走异步。
        """
        payload = {"workflow_id": workflow_id, "parameters": parameters}
        if bot_id:
            payload["bot_id"] = bot_id

        resp = self.session.post(f"{self.base_url}/v1/workflow/run",
                                 json=payload, timeout=timeout)
        resp.raise_for_status()
        body = resp.json()
        if body.get("code") != 0:
            raise RuntimeError(f"工作流失败[{body.get('code')}]：{body.get('msg')}")

        raw = body.get("data", "")          # data 是 JSON 字符串，不是对象
        try:
            return json.loads(raw)
        except (TypeError, json.JSONDecodeError):
            return raw

    def list_messages(self, conversation_id: str, chat_id: str | None = None, limit: int = 20):
        """查看会话消息列表：POST 请求，conversation_id 在 query，分页与过滤在 body。"""
        params = {"conversation_id": conversation_id}
        body = {"order": "desc", "limit": limit}
        if chat_id:
            body["chat_id"] = chat_id           # 只看某一次对话，过滤掉历史消息

        resp = self.session.post(f"{self.base_url}/v1/conversation/message/list",
                                 params=params, json=body, timeout=60)
        resp.raise_for_status()
        return resp.json().get("data", [])


def main():
    token = os.environ["COZE_API_TOKEN"]
    bot_id = os.environ["COZE_BOT_ID"]
    client = CozeClient(token, os.environ.get("COZE_BASE_URL", "https://api.coze.cn"))

    # 第一轮：不传 conversation_id，服务端自动建会话
    answer, conv_id, chat_id = client.chat(bot_id, "demo_user_001", "用一句话介绍你自己")
    print(f"回复：{answer}")
    print(f"conversation_id={conv_id}  chat_id={chat_id}")

    # 第二轮：带上 conversation_id 才会延续上下文
    client.chat(bot_id, "demo_user_001", "你刚才说了什么？", conversation_id=conv_id)

    # 工作流：parameters 的键名必须与开始节点定义的输入参数一致
    workflow_id = os.environ.get("COZE_WORKFLOW_ID")
    if workflow_id:
        print("工作流输出：", client.run_workflow(workflow_id, {"topic": "AI Agent"}, bot_id=bot_id))

    # 消息列表：type=answer 是回复，question 是用户输入，中间态消息默认不返回
    for msg in client.list_messages(conv_id, chat_id=chat_id, limit=5):
        print(msg.get("role"), msg.get("type"), (msg.get("content") or "")[:60])


if __name__ == "__main__":
    main()
```

> 官方另提供 Python SDK `cozepy`（`pip install cozepy`，用 `COZE_API_TOKEN` 初始化），封装了同样的接口、SSE 解析与流式迭代器。手写 HTTP 的价值在于看清协议本身：事件名在 `event:` 行、`conversation_id` 在 query、工作流 `data` 是 JSON 字符串。

## 六、3 个实战坑

### 坑 1：Bot 的提示词（人设）写得太简单——“你是一个旅游顾问”，结果是 Bot 回答泛泛、没有个性、经常超范围回答，质量不稳定

**现象**：团队用 Coze 构建客服 Bot，人设描述写得很简单——“你是一个专业的客服，回答用户问题”。运行后发现：①Bot 回答很泛泛，没有针对性（用户问“怎么退款”，Bot 回答“退款流程请查看帮助中心”，没有具体步骤）；②Bot 没有个性，所有回答都是“模板化”的，用户体验差；③Bot 经常超范围回答（用户问“你们老板是谁”，Bot 瞎编一个名字）；④Bot 遇到不知道的问题时，不会说“我不知道”，而是编造答案（幻觉）；⑤不同用户问同样的问题，Bot 的回答差异很大（质量不稳定）。团队以为是“模型不好”，换了几个模型还是不行——根因是提示词（人设）写得太简单，没有明确回答风格、知识边界、应对策略。

#### 避坑
- **Bot 的人设描述（System Prompt）必须包含四要素：身份定位、回答风格、知识边界、应对策略**：

  ```
  # ❌ 简单的人设
  "你是一个专业的客服，回答用户问题"

  # ✅ 完整的人设（四要素）
  "你是【XX品牌】的官方客服助手，名字叫小助手。

  ## 身份定位
  你是 XX 品牌的官方客服，负责解答用户关于产品、订单、售后的问题。
  你不是真人，你是 AI 助手，但你要用友好、专业的语气和用户交流。

  ## 回答风格
  - 语气：热情、耐心、专业，像朋友一样交流
  - 格式：回答要简洁明了，分点说明，重点内容加粗
  - 长度：一般问题 100 字以内，复杂问题不超过 300 字
  - 称呼：称呼用户为"亲"

  ## 知识边界
  - 你只回答关于 XX 品牌产品、订单、售后的问题
  - 不要回答与 XX 品牌无关的问题（如"今天天气怎么样"、"推荐一部电影"）
  - 不要回答公司内部信息（如"你们老板是谁"、"公司营收多少"）
  - 不要评价竞争对手
  - 所有回答必须基于知识库内容，不要编造信息

  ## 应对策略
  - 知识库中有答案：基于知识库内容回答，引用相关文档
  - 知识库中没有答案：如实说"抱歉，这个问题我暂时无法回答，建议您联系人工客服（400-XXX-XXXX）"，不要编造
  - 用户情绪激动：先安抚情绪（"非常抱歉给您带来不好的体验"），再解决问题
  - 用户要求转人工：立即提供人工客服联系方式，不要挽留
  - 涉及退款/赔偿等高风险操作：不要承诺具体金额，引导用户联系人工客服处理"
  ```

- **人设描述的最佳实践**：
  1. **用 Markdown 结构化**：用标题、列表、加粗让提示词层次清晰，模型更容易理解
  2. **给出正面示例和负面示例**：告诉模型“应该怎么做”和“不应该怎么做”
  3. **明确知识边界**：明确告诉模型“只回答什么”、“不回答什么”，防止超范围回答
  4. **明确“不知道时怎么办”**：告诉模型遇到不知道的问题时应该怎么应对（引导人工客服），防止幻觉
  5. **设置回答格式**：明确回答的长度、格式、语气，保证输出一致性
  6. **持续迭代**：根据对话日志和用户反馈，持续优化提示词

- **用“开场白”和“推荐问题”引导用户**：
  - 开场白：Bot 启动时自动发送的欢迎语，告诉用户“我能做什么”
  - 推荐问题：在输入框上方显示几个推荐问题，引导用户提问
  - 这两个功能可以有效引导用户在 Bot 的知识范围内提问，减少超范围问题

- **用“变量”实现个性化**：
  - Coze 支持自定义变量，可以在提示词中引用变量（如 `{{user_name}}`、`{{user_level}}`）
  - 调用 API 时传入变量，实现个性化回答（如“尊敬的 VIP 用户 {{user_name}}，您好”）
  - 变量也可以用于条件判断（如 VIP 用户走 VIP 专属流程）

- **类比**：就像“员工培训”——
  - 简单的培训 = “你是客服，好好干”——员工不知道具体怎么做，服务质量参差不齐
  - 完整的培训 = 员工手册（身份定位 + 服务规范 + 业务范围 + 应急预案）——员工知道 exactly 怎么做，服务质量稳定
  - Bot 的人设描述就是“员工手册”——写得越详细、越结构化，Bot 的表现越稳定、越符合预期
  - 不要指望 Bot“自己悟”——明确告诉它“应该怎么做”、“不应该怎么做”、“遇到 X 情况怎么办”

### 坑 2：知识库文档不预处理就上传——PDF 的页眉页脚、网页的导航栏广告、扫描件的 OCR 错误都被索引，结果是检索经常返回无关内容，Bot 回答质量差

**现象**：团队用 Coze 构建企业知识库，直接上传了各种文档：PDF 产品手册（带页眉页脚和目录）、网页文章（直接复制 URL，包含导航栏、广告、相关推荐）、扫描件（OCR 识别，有很多识别错误）、Word 制度文件（带修订痕迹和评论）。运行后发现：①检索经常返回无关内容——用户问“怎么退货”，检索返回的是“目录页”或“页眉页脚”；②网页文章的导航栏、广告、相关推荐也被索引，检索时经常返回这些无关内容；③扫描件的 OCR 错误导致检索不到正确内容（如“退货”被识别成“退贷”）；④Word 的修订痕迹和评论也被索引，导致内容混乱；⑤Bot 回答时经常引用无关内容，答案质量差。团队以为是“Embedding 模型不好”，换了模型还是不行——根因是文档没有预处理，大量“噪音”被索引。

#### 避坑
- **文档上传前必须预处理——去除“噪音”，只保留有价值的内容**：

  **PDF 文档预处理**：
  - 去除封面、目录、页眉、页脚、版权页
  - 去除空白页和重复页
  - 如果是扫描件，先用高质量 OCR 工具识别（如百度 OCR、腾讯 OCR、Adobe OCR），人工校对识别错误
  - 提取文本后，检查是否有乱码、格式错误
  - 大文件可以按章节拆分，每个章节单独上传（提高检索精度）

  **网页文章预处理**：
  - 不要直接复制 URL——用“阅读模式”或“网页正文提取工具”（如 Readability、Jina AI Reader）提取正文
  - 去除导航栏、页脚、广告、相关推荐、评论区
  - 去除无关的链接和图片描述
  - 只保留文章正文（标题 + 正文内容）

  **Word 文档预处理**：
  - 接受所有修订，去除修订痕迹
  - 删除所有评论
  - 去除页眉页脚
  - 检查是否有隐藏文字（白色文字、隐藏文本）
  - 统一格式（字体、字号、标题层级）

  **表格/结构化数据预处理**：
  - 确保表格有明确的表头
  - 去除空行和空列
  - 大表格可以按行拆分，每行作为一个独立的知识条目
  - 确保数据格式统一（如日期格式、金额格式）

- **分块策略要按文档形态定，不要一刀切**：
  - 技术文档/产品手册：按段落切，别把一张操作步骤切两半
  - 制度文件/法律文档：按条款切，保持“一条一款”完整
  - FAQ/问答对：一问一答一个片段，别跨对合并
  - 重叠（overlap）取分段长度的 10%~20%，让跨段语义有落点

- **检索参数按官方语义调**：
  - 最大召回数量：默认 5，调大只是把更多片段塞进上下文，未必更准
  - 最小匹配度：默认 0.5，且只在关闭结果重排时可设；开了重排这个参数直接失效
  - 搜索策略：混合（默认推荐）/ 语义（跨语言、近义改写）/ 全文（产品名、错误码、缩写、ID）
  - 查询改写：默认开启，多轮对话里明显提升召回；单轮短查询场景可关掉省一次模型调用

- **知识库的持续维护**：
  - 定期检查知识库内容，删除过时、错误、重复的文档
  - 根据对话日志，发现“检索不到”或“检索不准”的案例，针对性补充或优化文档
  - 新产品/新功能上线时，及时更新知识库
  - 建立知识库维护流程（谁负责更新、多久更新一次、更新标准是什么）

- **类比**：就像“图书馆整理”——
  - 不整理的图书馆 = 书乱堆，封面、目录、广告、废纸混在一起——找书时经常找到无关的东西
  - 整理好的图书馆 = 书分类上架，去除封面目录广告，每本书有清晰的索引——找书又快又准
  - Coze 知识库也是一样——文档预处理就是“图书馆整理”，去除噪音、分类整理、建立清晰索引，检索质量才会好
  - 不要把“垃圾”丢进知识库——“垃圾进，垃圾出”（Garbage In, Garbage Out）

### 坑 3：工作流设计得太复杂——几十个节点，嵌套多层条件分支，调试困难，出问题不知道哪里错了，而且每次运行都很慢（很多 LLM 节点串行）

**现象**：团队用 Coze 工作流构建一个“智能客服”流程，觉得“功能越全越好”，设计了一个包含 30+ 个节点的复杂工作流：问题分类（5 个类别）→ 每个类别有独立的处理流程（5-10 个节点）→ 每个处理流程又有条件分支和循环→ 最后汇总输出。运行后发现：①调试困难——出问题时不知道哪个节点错了，需要逐个节点检查；②维护成本高——修改一个小功能需要理解整个工作流的逻辑；③性能差——30 多个节点串行执行，其中有 10 个 LLM 节点，每个几秒，总响应时间 30+ 秒，用户等不及；④容易出错——复杂的条件分支和变量传递，经常出现变量未定义、类型不匹配；⑤Token 成本高——每次运行调用很多次 LLM，成本是简单工作流的 5-10 倍。团队觉得“Coze 工作流不好用”，但其实是“过度设计”——把简单问题复杂化了。

#### 避坑
- **工作流设计原则：保持简单，能用 5 个节点解决就不用 10 个——复杂的逻辑尽量用代码节点处理，不要用大量条件分支节点**：

  **简化策略 1：用代码节点替代复杂的条件分支**
  - 如果有很多条件分支（if-else 嵌套 3 层以上），考虑用一个代码节点（Python/JS）处理
  - 代码节点可以处理复杂的逻辑判断、数据转换、变量计算
  - 比一堆条件分支节点更简洁、更易维护、性能更好（代码执行比 LLM 快得多）

  **简化策略 2：用 Bot/Agent 替代固定工作流**
  - 如果任务流程不固定，需要根据情况动态决策，考虑用 Agent（带插件）而不是固定工作流
  - Agent 可以自主决定“下一步做什么”、“调用哪个插件”
  - 比固定工作流更灵活，适合复杂的、不确定的任务
  - 但 Agent 的可预测性和成本控制不如固定工作流，需要权衡

  **简化策略 3：拆分子工作流**
  - 如果工作流有多个独立的处理流程，考虑拆成多个子工作流
  - 主工作流负责调度，子工作流负责具体处理
  - 子工作流可以独立测试、独立维护、复用
  - Coze 支持“工作流作为插件”，可以在主工作流中调用子工作流

  **简化策略 4：合并功能相似的 LLM 节点**
  - 如果有多个 LLM 节点做相似的事情，考虑合并成一个
  - 例如：“问题分类”和“意图识别”可以合并成一个 LLM 节点
  - 减少 LLM 节点数量，可以显著降低响应时间和成本

  **简化策略 5：用批处理节点并行**
  - 如果有多个独立的分支（如同时查多个数据源），可以把它们放进批处理节点并行处理
  - 扣子工作流没有 Dify 式的“并行节点”，批量并发靠批处理节点实现
  - 注意并发会放大付费节点（模型、插件）的瞬时计费

- **工作流的调试技巧**：
  - **用试运行看节点级 I/O**：跑通后每个节点右上角可看输入输出，失败节点边框变色
  - **看 debug_url**：调 `/v1/workflow/run` 返回的 debug_url 能可视化回看每次执行的节点输入输出（7 天有效）
  - **加临时输出节点**：把中间变量接到输出节点，验证数据形状再往下接
  - **从简单开始**：先跑通最小版本，再加一个功能测一次
  - **看对话日志**：智能体侧的对话日志能定位到哪一步没按预期走

- **工作流的性能优化**：
  - **减少大模型节点数量**：每次模型调用都要等，能合并就合并
  - **把确定性的活交给代码或 SQL 节点**：判断、清洗、拼接不需要模型
  - **按任务难度分模型**：简单任务用小模型，复杂推理才上大模型
  - **注意超时**：非流式 `/v1/workflow/run` 90 秒无响应即断开，整体超时 10 分钟；长任务走 stream_run 或付费套餐的 is_async
  - **把重复查询结果存下来**：用数据库或变量节点缓存，别每次都重跑一遍模型

- **工作流的命名和文档**：
  - 每个节点都要有清晰的命名（如“问题分类”、“产品知识检索”、“生成回答”），不要用默认的“LLM 节点 1”
  - 复杂的工作流要写文档说明整体逻辑、每个节点的作用、变量传递关系
  - 方便团队协作和后续维护

- **类比**：就像“写代码”——
  - 一个函数写 1000 行，嵌套 10 层 if-else = 难以调试、难以维护、容易出错
  - 好的代码 = 函数拆分（每个函数做一件事）、减少嵌套、清晰命名、写注释
  - Coze 工作流也是一样——节点就像代码语句，工作流就像函数
  - 不要把所有逻辑都堆在一个工作流里——拆分成子工作流、用代码节点处理复杂逻辑、保持简洁
  - “简单就是美”（KISS 原则）在工作流设计中同样适用

## 七、进阶问题（引导往下挖）

### 问题 1：Coze 的“零代码”和 LangChain/LangGraph 的“代码优先”各有什么优劣势？在团队中应该如何分工——哪些人用 Coze，哪些人用 LangChain？两者可以结合使用吗？

#### 引导思考
- **零代码（Coze）的本质**：
  - 把 AI 应用开发抽象为“可视化配置”——拖拽节点、填写表单、选择选项
  - 目标用户是非技术用户（运营、产品、营销、客服）
  - 核心价值是“降低门槛”——不需要编程能力，也能构建 AI 应用
  - 类比：建站工具（Wix/Squarespace）——拖拽式建站，不需要写代码

- **代码优先（LangChain/LangGraph）的本质**：
  - 把 AI 应用开发抽象为“代码编写”——用 Python/JS 代码定义逻辑
  - 目标用户是开发者（工程师、数据科学家、研究者）
  - 核心价值是“灵活性和控制力”——完全自定义，不受平台限制
  - 类比：Web 开发框架（React/Next.js）——完全用代码构建，灵活强大

- **零代码的优势**：
  1. **上手快**：非技术用户也能在几分钟内构建一个可用的 AI Bot
  2. **可视化**：逻辑一目了然，便于理解和沟通
  3. **内置能力丰富**：RAG、插件、工作流、发布渠道都内置，不需要自己组装
  4. **一键发布**：发布到多个渠道（抖音/飞书/微信/API），不需要自己搭后端
  5. **团队协作**：非技术用户可以独立完成，不需要占用开发者资源
  6. **迭代快**：修改配置即时生效，快速试错

- **零代码的劣势**：
  1. **灵活性有限**：受平台预定义节点和功能的限制，复杂逻辑可能无法实现或实现起来很别扭
  2. **代码扩展性差**：自定义逻辑需要写代码节点或插件，不如纯代码灵活
  3. **供应商锁定**：深度使用平台后，迁移到其他平台成本高
  4. **数据控制弱**：云服务版本数据在平台上，自托管能力弱（Coze 开源版功能有限）
  5. **调试能力有限**：虽然有节点级追踪，但不如代码调试器强大
  6. **复杂工作流维护困难**：节点太多时，可视化图变得混乱，难以维护

- **代码优先的优势**：
  1. **灵活性最高**：完全用代码控制，可以实现任意复杂的逻辑
  2. **代码扩展性好**：可以复用 Python/JS 生态的所有库和工具
  3. **版本控制顺畅**：纯代码，Git 协作、Code Review、CI/CD 都很顺畅
  4. **调试能力强**：可以用 Python 调试器、断点、日志，调试体验好
  5. **生产级特性成熟**：LangGraph 的 Checkpoint、Interrupt、时间旅行、流式、可观测性都很成熟
  6. **无供应商锁定**：纯代码，可以部署到任何环境
  7. **数据完全控制**：自托管，数据在自己服务器

- **代码优先的劣势**：
  1. **学习曲线陡**：需要理解 LangChain/LangGraph 的概念，需要编程能力
  2. **开发成本高**：需要写代码、搭后端、部署，从原型到生产的链路长
  3. **需要自己组装**：RAG、模型管理、可观测性都需要自己组装（虽然 LangChain 提供组件）
  4. **非技术用户无法使用**：必须有编程能力
  5. **发布渠道需要自己开发**：需要自己开发前端、对接各平台 API

- **团队分工建议**：

  **用 Coze 的人/场景**：
  - **运营团队**：构建营销 Bot、客服 Bot、内容创作 Bot——快速上线，快速迭代
  - **产品经理**：快速验证产品原型，做 MVP 测试
  - **客服团队**：构建 FAQ Bot、智能客服，基于知识库回答常见问题
  - **销售团队**：构建销售助手、客户跟进 Bot
  - **HR 团队**：构建 HR 助手、招聘 Bot、员工服务 Bot
  - **简单的内部工具**：如“会议纪要整理 Bot”、“文档翻译 Bot”
  - **需要快速上线、流量变现的场景**：如抖音小程序 Bot、飞书助手

  **用 LangChain/LangGraph 的人/场景**：
  - **开发团队**：构建复杂的、需要深度定制的 AI 应用
  - **数据科学家/研究者**：做研究、实验、算法优化
  - **企业级核心系统**：如智能决策系统、自动化工作流引擎、多 Agent 协作系统
  - **需要数据控制和安全合规的场景**：如金融、医疗、法律等受监管行业
  - **需要复杂逻辑和算法的场景**：如高级 RAG、多 Agent 协作、复杂推理
  - **需要高并发和高性能的场景**：如面向大量用户的生产系统
  - **需要深度集成现有系统的场景**：如与企业内部系统（ERP/CRM/数据库）深度集成

- **两者结合使用的架构**：

  **模式 1：Coze 做前端，LangChain 做后端复杂逻辑**
  - Coze Bot 作为用户交互前端（对话界面、多渠道发布）
  - Coze 工作流中调用 HTTP API → LangGraph 服务（处理复杂逻辑）
  - LangGraph 返回结果给 Coze，Coze 展示给用户
  - 优势：Coze 的快速开发和多渠道发布 + LangGraph 的复杂能力

  **模式 2：LangChain 做编排，Coze 做 RAG 工具**
  - LangGraph Agent 做整体编排（任务分解、工具选择、循环控制）
  - LangGraph 调用 Coze API（Coze 应用作为工具，处理 RAG 检索和回答）
  - Coze 返回结果给 LangGraph
  - 优势：LangGraph 的编排能力 + Coze 的 RAG 能力和知识库管理

  **模式 3：Coze 做 MVP，验证后迁移到 LangChain**
  - 阶段 1：用 Coze 快速构建 MVP，验证需求和市场
  - 阶段 2：如果验证成功且需要复杂能力/数据控制，用 LangChain/LangGraph 重构
  - 优势：快速验证 + 生产级重构，降低早期风险

  **模式 4：分层协作**
  - 简单的、通用的 Bot：用 Coze（运营团队自己维护）
  - 复杂的、核心的系统：用 LangChain（开发团队维护）
  - 两者通过 API 集成，各司其职
  - 优势：各取所长，非技术用户和开发者都有合适的工具

- **类比**：就像“公司的工具分工”——
  - Coze = 办公软件（Excel/PPT/钉钉）——非技术员工用，快速完成日常工作
  - LangChain = 专业开发工具（IDE/代码框架）——开发者用，构建复杂的核心系统
  - 公司不会让所有人都用专业开发工具——运营用 Excel 做报表就够了，不需要写代码
  - 公司也不会让核心系统用办公软件搭建——核心系统需要专业开发，保证性能和安全
  - 两者共存，各司其职——运营用 Coze 快速构建营销 Bot，开发用 LangChain 构建核心系统，两者通过 API 集成
  - Coze vs LangChain 也是一样——不是“二选一”，而是“根据用户和场景选择合适的工具”

### 问题 2：扣子的“长期任务”（Agent Plan）和“触发器（定时任务）”有什么本质区别？长期任务的出现意味着扣子从“聊天工具”向什么方向演进？长周期自主执行的 Agent 有哪些挑战和风险？

#### 引导思考

先对齐事实：这两个功能在扣子里是分开的两件事。

- **触发器（Trigger）**：官方能力，分定时触发与事件触发（Webhook）。触发后可执行三种任务——发一条自然语言指令给智能体、调用插件、调用工作流。限制很硬：每个智能体最多 10 个触发器；低代码智能体的触发器仅在飞书渠道生效；绑定的工作流或插件需在 1 分钟内跑完且关闭流式输出；功能目前处于“升级中”，暂不支持为新低代码智能体添加。
- **长期任务（Agent Plan / 长期计划）**：2026 年 1 月随 2.0 发布的模式，给定目标与完成方式后由 Agent 自主分解步骤、持续执行、主动汇报，官方描述可跨数小时到数天。

- **触发器（定时任务）的本质**：
  - 时间驱动或事件驱动——到点（或收到 Webhook）就执行预设任务
  - 任务是固定的——执行什么、怎么执行，都是预先定义好的
  - 执行是“一次性”的——执行完就结束
  - 没有“自主性”——不会根据中间结果调整计划
  - 类比：闹钟——到点响铃，响完就结束，不会根据你的状态调整

- **Agent Plan（长周期自主执行）的本质**：
  - Agent Plan 是“目标驱动”的——给定一个长期目标，Agent 自主规划和执行
  - 任务是“动态”的——Agent 根据目标自主分解任务、制定计划、调整策略
  - 执行是“持续性”的——可以持续数小时、数天、数月，不断推进目标
  - 有“自主性”——根据中间结果调整计划，自主决定下一步做什么，遇到问题自己解决
  - 有“记忆”——记住之前做了什么、学到了什么，基于记忆持续推进
  - 类比：员工——你给员工一个目标（“一周内完成市场调研报告”），员工自己规划（第一天收集资料，第二天分析，第三天撰写），每天汇报进展，遇到问题自己解决，最终交付报告

- **两者的核心区别**：

  | 维度 | 触发器（定时/事件触发） | 长期任务（Agent Plan） |
  |------|------------|--------------------------|
  | 驱动方式 | 时间驱动（到点执行） | 目标驱动（给定目标，自主推进） |
  | 任务定义 | 固定（预定义） | 动态（自主分解和调整） |
  | 执行时长 | 一次性（执行完结束） | 持续性（数小时/数天/数月） |
  | 自主性 | 无（按预设执行） | 高（自主决策、调整计划） |
  | 记忆 | 无（每次执行独立） | 有（跨步骤记忆，持续学习） |
  | 中间结果处理 | 不处理（执行完就结束） | 处理（根据中间结果调整计划） |
  | 问题解决 | 不解决（出错就报错结束） | 自主解决（遇到问题自己想办法） |
  | 类比 | 闹钟 | 员工 |

- **Agent Plan 意味着 Coze 的演进方向**：

  **从“聊天机器人平台”到“自主任务执行平台”**：
  - 传统的 Coze Bot 是“响应式”的——用户问一句，Bot 答一句
  - Agent Plan 让 Bot 变成“主动式”的——给定目标，Bot 主动规划、执行、推进，不需要用户每一步都指挥
  - 这意味着 Coze 从“对话工具”演进为“任务执行工具”——Bot 不只是“聊天”，而是“干活”

  **从“单轮交互”到“长周期协作”**：
  - 传统的 Bot 交互是“单轮”或“多轮对话”——每次交互是独立的或短期的
  - Agent Plan 支持“长周期协作”——用户和 Bot 可以在数天/数周的时间里协作完成一个复杂目标
  - Bot 会定期向用户汇报进展，用户可以随时干预和调整
  - 这意味着 Coze 从“即时工具”演进为“长期协作伙伴”

  **从“工具集成”到“能力封装”**：
  - 传统的 Bot 是“工具调用”——Bot 调用插件完成特定操作
  - Agent Plan 是“能力封装”——Agent Skills 把专业能力打包成可安装的模块，Bot 安装后即具备专业能力
  - 这意味着 Coze 从“工具平台”演进为“能力市场”——用户可以购买/安装各种专业能力

  **从“个人助手”到“数字员工”**：
  - 传统的 Bot 是“个人助手”——帮助个人完成简单任务
  - Agent Plan 让 Bot 变成“数字员工”——可以承担复杂的、长周期的工作任务，如市场调研、数据分析、内容创作、客户跟进
  - 这意味着 Coze 从“消费级工具”演进为“企业级生产力工具”

- **长周期自主执行 Agent 的挑战**：

  **挑战 1：规划能力**
  - 长周期任务需要 Agent 具备良好的规划能力——把大目标分解为可执行的小任务，制定合理的时间表
  - 当前 LLM 的规划能力还不够强，可能规划不合理（如任务分解太粗/太细、时间安排不合理）
  - 需要人工监督和调整，不能完全放手

  **挑战 2：中间结果评估和调整**
  - 长周期任务需要 Agent 能够评估中间结果，判断“是否在正确的轨道上”，如果偏离目标，及时调整计划
  - 当前 LLM 的自我评估能力有限，可能“一条路走到黑”，不会及时调整
  - 需要设置检查点，定期人工评估和干预

  **挑战 3：长期记忆管理**
  - 长周期任务需要 Agent 记住数天/数周前做了什么、学到了什么
  - 长期记忆的存储、检索、遗忘都是挑战——记忆太多会干扰当前决策，记忆太少会丢失重要信息
  - 需要有效的记忆管理策略（如记忆摘要、重要性评分、遗忘机制）

  **挑战 4：错误恢复和容错**
  - 长周期任务执行时间长，中间某个步骤出错的概率高
  - Agent 需要能够检测错误、从错误中恢复、重试或换一种方法
  - 当前 LLM 的错误恢复能力有限，可能“卡住”或“重复同样的错误”
  - 需要设置错误处理机制（如最大重试次数、降级策略、人工介入）

  **挑战 5：成本控制**
  - 长周期任务持续数天/数周，调用 LLM 的次数很多，成本可能很高
  - 需要成本控制策略（如用便宜的模型做简单任务、设置每日预算上限、缓存重复查询）
  - 需要实时监控成本，防止“失控”

  **挑战 6：可解释性和可审计性**
  - 长周期任务的决策过程复杂，用户可能不理解“Agent 为什么这么做”
  - 需要可解释性——Agent 应该能够解释自己的决策和行动
  - 需要可审计性——记录 Agent 的每一步操作，便于事后审计和复盘

- **长周期自主执行 Agent 的风险**：

  **风险 1：目标漂移（Goal Drift）**
  - Agent 在执行过程中可能偏离原始目标，去做“看起来相关但其实不重要”的事情
  - 例如：目标是“写一份市场调研报告”，Agent 可能花大量时间研究“市场调研的方法论”，而不是实际做调研
  - 缓解：明确目标边界，定期检查是否在正确轨道上，设置“完成标准”

  **风险 2：过度探索（Over-exploration）**
  - Agent 可能“过度探索”——调用很多工具、做很多无关的尝试，导致成本高、效率低
  - 例如：为了回答一个简单问题，Agent 搜索了 100 个网页、调用了 10 个工具
  - 缓解：限制工具调用次数、设置最大步数、用“探索 vs 利用”平衡策略

  **风险 3：不可控的自主行为**
  - 长周期自主执行的 Agent 可能做出“意料之外”的行为——如发送了不该发的邮件、删除了不该删的数据
  - 特别是如果 Agent 有“写操作”权限（发送邮件、修改数据、发布内容），风险更大
  - 缓解：最小权限原则（只给必要的权限）、高风险操作需要人工确认、设置操作边界

  **风险 4：幻觉和错误信息**
  - 长周期任务中，Agent 可能产生幻觉（编造信息）或传播错误信息
  - 特别是在信息不足时，Agent 可能“编造”数据来填补空白
  - 缓解：要求 Agent 引用来源、设置事实核查步骤、人工审核关键输出

  **风险 5：安全漏洞（Prompt 注入）**
  - 长周期 Agent 会读取大量外部内容（网页、邮件、文档），可能受到间接 Prompt 注入攻击
  - 攻击者可能在 Agent 读取的内容中藏入恶意指令，劫持 Agent 行为
  - 缓解：输入过滤、工具权限控制、沙箱隔离、输出过滤（参考 Agent 安全知识点）

  **风险 6：依赖和信任问题**
  - 用户可能过度依赖 Agent，失去独立判断能力
  - Agent 的错误可能导致用户做出错误决策
  - 缓解：明确 Agent 的能力边界、关键决策需要人工审核、保持人类在环

- **类比**：就像“从闹钟到员工”的演进——
  - 传统定时任务 = 闹钟——到点响铃，响完就结束，简单可靠但功能有限
  - Agent Plan = 员工——给目标，自己规划执行，持续推进，灵活强大但需要管理
  - 从闹钟到员工是“进化”——能力更强，但管理成本也更高
  - 员工需要管理（目标设定、进度检查、绩效评估、成本控制），Agent Plan 也一样
  - Coze 从“聊天机器人”演进为“自主任务执行平台”，就像从“卖闹钟”演进为“提供数字员工”
  - 这是 AI 应用的发展趋势——从“工具”到“助手”到“员工”，自主性越来越强，能力越来越大，但管理和安全的挑战也越来越大

- 延伸：后续知识点（生产级 Agent 架构设计）会深入讲解长周期自主执行 Agent 的架构设计、管理策略、安全防护和成本控制

## 八、四关自测

### 复述关（3句话讲清）

1. **扣子是字节跳动的 AI Agent 平台，现在是“双主线”**：扣子做对话式的 AI 团队协作（人 + 多 Agent 在项目里干活），扣子编程做 Vibe Coding 开发（对话生成智能体、工作流、网页、App、小程序并一键部署），旧的低代码开发平台已不对新用户开放。
2. **它给 Agent 加能力的方式是三层而不是一堆插件**：技能管“怎么干”（方法、步骤、经验），MCP 管“连什么”（外部工具与数据），插件把技能 + MCP + 可选的 Panel 打包成可安装能力；再叠加工作流编排、知识库、记忆与触发器，才构成能交付结果的系统。
3. **它和 Dify/LangChain 的分工不是“谁更强”**：要快、要渠道分发、要非技术同事自己维护，用扣子；要数据自托管、要细粒度控制、要做核心系统，用 Dify 或 LangGraph。开源版 Coze Studio 只是补了自托管这一块，不能当商业版的等价替代。

### 举例关（真实场景）

运营要在 3 天内给微信服务号上线一个“产品 FAQ 客服”：把产品手册预处理后传进扣子知识库（选混合搜索、召回数默认 5），拖一条“用户问题 → 知识库检索 → 命中就答、没命中转人工”的工作流，挂一个查订单的插件，发布到微信服务号或订阅号渠道。全程不写后端代码，运营自己改话术和知识库，上线后看对话日志与 debug_url 定位问题——这是扣子最典型的落地姿势。

### 反例关（边界条件）

如果要对接公司 ERP/CRM、带细粒度权限、日活十万级、还要和现有微服务深度集成，硬上扣子会踩坑：商业版数据在平台侧、代码节点受平台限制、高并发与供应商锁定都是硬伤，开源版又更新滞后、缺能力。这类场景正确做法是用 LangGraph 自建服务，只用扣子做前端 MVP 验证。另外长周期任务（Agent Plan）如果不设步数上限和人工审批，容易目标漂移、乱花钱——自主执行不能完全放手。

### 教学关（给小白讲）

把扣子想象成“AI 版的乐高店 + 自动开店机”：你不会烧砖画图（写代码）也没关系，店里有现成的积木块——会搜网页的、会查资料的、会发消息的，还有行业老师傅写好的“操作手册”（技能）。你像拼乐高一样把积木拖到板子上连好线，把公司说明书（知识库）摆进去，最后点一下“开张”，AI 小店就出现在飞书、微信、抖音小程序里。顾客问问题，它先翻说明书再答，答不上来就转真人。记住一句：乐高店适合开小店试水，真要盖摩天大楼（核心系统），还是得找专业施工队（写代码的框架）。
