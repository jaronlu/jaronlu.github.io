## 一、结论前置

1. **Agent 的 Prompt 工程和普通 LLM 调用的 Prompt 工程有本质区别——普通 Prompt 只需要指导“一次回答”，Agent 的 System Prompt 需要指导“几十轮对话、多次工具调用、边界情况处理、错误恢复”，是 Agent 行为的“宪法”**。Agent Prompt 工程的三大支柱是：①**System Prompt**（定义身份、边界、决策流程、行为规则）；②**工具描述**（让模型准确知道什么时候调用哪个工具、怎么传参数）；③**少样本示例**（展示复杂推理模式，2-3 个示例是准确性和成本的最佳平衡）。
2. **一个好的 Agent System Prompt 要回答九个问题**：①身份（你是谁？专长是什么？）②目标（你要完成什么？）③能力和边界（你能做什么？不能做什么？）④可用工具（有哪些工具？什么时候用？）⑤输出格式（思考/行动/最终答案分别是什么格式？）⑥决策指南（遇到情况怎么判断？）⑦质量标准（什么是好的输出？）⑧错误处理（工具失败/信息不足怎么办？）⑨关键提醒（最重要的规则重复强调）。华为云总结为“四定”：定身份、定边界、定流程、定格式。
3. **Agent Prompt 优化的核心方法论是“从简单开始，用 traces 驱动迭代”**——不要一开始就写几百行的复杂 Prompt，先写一个简单版本跑起来，收集失败案例（traces），针对具体的失败模式优化 Prompt（加规则、加示例、改工具描述），然后 A/B 测试验证。关键洞察：**在有 traces 之前不要调优**——没有真实失败案例的“优化”往往是瞎猜。另外，**定义边界（DO NOT）和定义任务（DO）同样重要**——自主运行的 Agent 必须知道什么不能做，而不只是应该做什么。

## 二、通俗类比 + 专业定义

### 通俗类比

#### Agent 的 System Prompt = 新员工的入职手册 + 岗位说明书

- **入职手册（System Prompt）**：
  - 公司介绍和你的角色（“你是客服部的技术支持专员”）
  - 你的职责和目标（“帮助用户解决技术问题，让用户满意”）
  - 你能做什么、不能做什么（“可以查询订单、发起退款；不能修改价格、不能承诺超出权限的事”）
  - 工作流程（“先了解用户问题→查询知识库→如果解决不了升级给工程师→最后确认用户满意”）
  - 工具使用指南（“CRM 系统查用户信息，工单系统创建工单，不要用错系统”）
  - 输出规范（“回复用户要用礼貌用语，技术问题要给出具体步骤，不要只说‘请稍等’”）
  - 质量标准（“回复要准确、及时、友好；不能编造信息；不确定时要承认并升级”）
  - 错误处理（“如果系统查询失败，告诉用户稍后再试并记录问题；如果用户不满意，主动道歉并寻求解决方案”）
  - 重要提醒（“绝对不能泄露其他用户的信息！绝对不能承诺退款超过你的权限！”）

- **为什么入职手册很重要？**
  - 新员工（Agent）刚入职，什么都不知道，需要明确的指导
  - 员工（Agent）会自主工作，主管（开发者）不可能每一步都盯着
  - 如果手册写得好，员工（Agent）就能独立处理大部分情况
  - 如果手册写得不好，员工（Agent）就会犯各种错误（越权、答非所问、流程混乱）

- **和普通 Prompt 的区别**：
  - 普通 Prompt = 一次性任务的指令（“帮我写一封邮件”）——就像临时找个帮工，告诉他这一件事怎么做
  - Agent System Prompt = 岗位说明书——就像招一个正式员工，告诉他这个岗位的所有职责、流程、规范、边界，他会长期自主工作

### 专业定义

| 概念 | 定义 |
|------|------|
| **Agent System Prompt（智能体系统提示词）** | 在 Agent 的每次 API 调用中都会发送的持久性指令集，模型将其视为高优先级。它定义了 Agent 的身份、目标、能力边界、决策流程、工具使用指南、输出格式、质量标准和错误处理方式，是控制 Agent 行为的最强大杠杆。 |
| **Tool Description（工具描述）** | 对 Agent 可用工具的名称、功能、参数、使用时机的描述。好的工具描述让模型能准确判断“什么时候调用这个工具”和“怎么传参数”，是 Function Calling 准确性的关键。 |
| **Few-shot Examples（少样本示例）** | 在 Prompt 中提供的 2-3 个完整的输入-输出示例，展示期望的推理模式和行为。对于 Agent 无法自行发现的复杂推理模式（如 ReAct 的思考-行动-观察循环、特定的决策流程），少样本示例比纯文字描述更有效。 |
| **ReAct Prompt（ReAct 提示词）** | 指导 Agent 按照 ReAct 模式（思考→行动→观察→思考...）交替进行推理和工具调用的 Prompt。关键是明确标记每个阶段（Thought/Action/Observation），定义工具使用规范，并提供示例展示期望的行为。 |
| **Boundary Definition（边界定义）** | 在 Prompt 中明确规定 Agent 能做什么（DO）和不能做什么（DO NOT）。对于自主运行的 Agent，定义“不能做什么”和定义“应该做什么”同样重要——边界防止 Agent 越权、做危险操作或产生不可控行为。 |
| **Output Format Control（输出格式控制）** | 在 Prompt 中明确规定 Agent 输出的格式（如 JSON Schema、特定的标记结构、字段要求）。对于 Agent，输出格式控制尤其重要——因为 Agent 的输出会被下游代码解析（如工具调用参数、结构化状态更新），格式不稳定会导致解析失败。 |
| **Prompt Iteration（提示词迭代）** | 基于真实运行数据（traces）持续优化 Prompt 的过程。方法论是：从简单 Prompt 开始→收集失败案例→针对失败模式优化→A/B 测试验证→重复。关键原则是“在有 traces 之前不要调优”。 |
| **Context Window Management for Prompt（提示词的上下文窗口管理）** | 在有限的上下文窗口中合理分配空间给 System Prompt、对话历史、工具结果和少样本示例。Agent 的上下文窗口很容易被长对话历史和工具结果撑爆，需要策略性地管理（如摘要压缩、滑动窗口、关键信息优先）。 |

## 三、底层机制

### 一、Agent System Prompt 的九段式结构

一个生产级的 Agent System Prompt 通常包含以下九个部分：

```
┌─────────────────────────────────────────────────────────┐
│  1. 身份与角色（Identity & Role）                         │
│     "你是 XX 公司的技术支持 Agent，专注于解决用户的技术问题" │
├─────────────────────────────────────────────────────────┤
│  2. 目标与职责（Goal & Responsibilities）                  │
│     "你的目标是帮助用户快速解决技术问题，提升用户满意度"      │
├─────────────────────────────────────────────────────────┤
│  3. 能力与边界（Capabilities & Boundaries）               │
│     DO: 查询知识库、创建工单、查询订单状态                   │
│     DO NOT: 修改价格、承诺退款、泄露其他用户信息             │
├─────────────────────────────────────────────────────────┤
│  4. 可用工具（Available Tools）                            │
│     - search_knowledge_base: 当用户提出技术问题时使用       │
│     - create_ticket: 当问题无法在知识库中找到答案时使用      │
│     - query_order: 当用户询问订单相关问题时使用              │
├─────────────────────────────────────────────────────────┤
│  5. 决策流程（Decision-Making Workflow）                   │
│     1. 理解用户问题                                        │
│     2. 判断是否需要查询信息 → 是则调用 search_knowledge_base │
│     3. 判断是否能解决 → 不能则 create_ticket 并告知用户     │
│     4. 给出解决方案并确认用户满意                            │
├─────────────────────────────────────────────────────────┤
│  6. 输出格式（Output Format）                              │
│     思考格式: Thought: [你的思考]                           │
│     行动格式: Action: [工具名](参数)                        │
│     最终答案: Final Answer: [给用户的回复]                   │
├─────────────────────────────────────────────────────────┤
│  7. 质量标准（Quality Standards）                          │
│     - 回答必须准确，不能编造信息                             │
│     - 技术问题要给出具体可执行的步骤                         │
│     - 不确定时要承认并升级，不要瞎猜                         │
├─────────────────────────────────────────────────────────┤
│  8. 错误处理（Error Handling）                             │
│     - 工具调用失败: 重试一次，仍失败则告知用户稍后再试       │
│     - 信息不足: 主动向用户询问必要信息                       │
│     - 用户不满意: 道歉并寻求替代方案                         │
├─────────────────────────────────────────────────────────┤
│  9. 关键提醒（Critical Reminders）                         │
│     ⚠️ 绝对不能泄露其他用户的信息！                          │
│     ⚠️ 绝对不能承诺超出你权限的退款或赔偿！                   │
└─────────────────────────────────────────────────────────┘
```

#### 各部分的重要性排序（根据实际调试经验）
1. **边界定义（DO/DO NOT）**——最容易出问题的地方，自主 Agent 经常越权
2. **决策流程**——Agent 不知道“先做什么后做什么”时会混乱
3. **工具使用指南**——工具调用错误是 Agent 最常见的失败模式
4. **输出格式**——格式不稳定会导致下游解析失败
5. **身份和目标**——设定基调，但不是最关键的
6. **质量标准**——提升输出质量，但优先级低于“不出错”
7. **错误处理**——减少失败时的影响
8. **少样本示例**——对复杂推理模式有效
9. **关键提醒**——对最重要的规则重复强调（长 Prompt 中模型可能忽略前面的规则）

### 二、工具描述（Tool Description）的设计

工具描述是 Function Calling 准确性的关键——模型根据工具描述决定“要不要调用”和“怎么传参数”。

#### 好的工具描述包含四个要素

```python
tools = [
    {
        "type": "function",
        "function": {
            "name": "search_knowledge_base",  # ① 名称：清晰描述功能
            "description": (
                "当用户提出技术问题、产品使用问题或故障排查问题时，"
                "调用此工具搜索公司知识库获取答案。"
                "不要用于查询订单状态、价格或用户个人信息。"  # ② 描述：什么时候用 + 什么时候不用
            ),
            "parameters": {
                "type": "object",
                "properties": {
                    "query": {
                        "type": "string",
                        "description": "搜索关键词，应该是具体的技术术语或问题描述，"
                                     "例如'如何重置密码'、'应用白屏怎么办'。"  # ③ 参数描述：类型 + 含义 + 示例
                    },
                    "category": {
                        "type": "string",
                        "enum": ["technical", "product", "billing"],  # ④ 枚举：限定可选值，减少错误
                        "description": "问题分类，帮助缩小搜索范围"
                    }
                },
                "required": ["query"]  # ⑤ 必填字段
            }
        }
    }
]
```

#### 工具描述的常见错误
| 错误 | 后果 | 修正 |
|------|------|------|
| 名称太模糊（如 `do_search`） | 模型不知道这个工具是搜什么的 | 名称要具体（`search_knowledge_base`） |
| 描述只说“搜索信息” | 模型无法判断什么时候该用 | 说明“什么时候用”+“什么时候不用” |
| 参数描述太简单（`query: string`） | 模型不知道该传什么格式 | 说明参数含义、格式、示例值 |
| 没有枚举限制 | 模型可能传入无效的分类值 | 用 enum 限定可选值 |
| 工具太多 | 模型选择困难，调用错误率上升 | 分组/预选择/动态加载工具 |
| 工具功能重叠 | 模型不知道该用哪个 | 合并相似工具，或明确区分使用场景 |

#### 工具数量的最佳实践
- 少量、精设计（约 10-20 个以内）：LLM 直接选择，效果好。Anthropic 官方口径是“少而精、按高价值工作流设计工具”，Claude Code 实践约 15-20 个
- 工具更多时可靠性开始下降：需要检索预选择（先检索相关工具，再让 LLM 选择）或命名空间分组
- 大规模工具集：需要动态发现机制（如 MCP 的工具发现协议）。具体阈值没有可靠来源（各模型差异大），以上限数字为经验估计，按自身评测确定

### 三、少样本示例（Few-shot Examples）的设计

少样本示例是展示“期望行为”的最有效方式——特别是对于 Agent 无法自行发现的复杂推理模式。

#### 好的少样本示例包含
1. **完整的输入-输出对**：从用户输入到 Agent 的完整推理过程（思考→行动→观察→最终答案）
2. **覆盖典型场景**：包括正常流程、边界情况、错误处理
3. **2-3 个示例**：是准确性提升和上下文成本的最佳平衡（更多示例边际收益递减）

#### ReAct 模式的少样本示例
```
## 示例 1：正常流程

用户：如何重置我的密码？

Thought：用户问的是密码重置，这是一个常见的技术问题。我应该先搜索知识库获取标准答案。
Action：search_knowledge_base(query="如何重置密码", category="technical")
Observation：密码重置步骤：1. 点击登录页的"忘记密码" 2. 输入注册邮箱 3. 查收重置邮件 4. 设置新密码

Thought：知识库中有明确的答案，我可以直接告诉用户步骤。
Final Answer：重置密码的步骤如下：
1. 点击登录页面的"忘记密码"链接
2. 输入您的注册邮箱地址
3. 查收邮件并点击重置链接
4. 设置您的新密码

如果您没有收到邮件，请检查垃圾邮件文件夹，或联系客服协助。

## 示例 2：需要升级的情况

用户：我的账户被锁定了，怎么解锁？

Thought：账户锁定可能涉及安全验证，知识库中可能没有具体的解锁流程（因为需要人工审核）。我先搜索一下。
Action：search_knowledge_base(query="账户被锁定如何解锁", category="technical")
Observation：未找到相关结果。账户锁定通常需要安全团队人工审核解锁。

Thought：知识库中没有答案，这种情况需要创建工单让人工处理。我应该创建工单并告知用户。
Action：create_ticket(title="账户解锁请求", description="用户账户被锁定，需要人工审核解锁", priority="high")
Observation：工单已创建，工单号：TICKET-2026-1005

Thought：工单已创建，我应该告知用户工单号和预计处理时间。
Final Answer：您的账户锁定问题需要安全团队人工审核处理。
我已为您创建了高优先级工单，工单号：TICKET-2026-1005
预计处理时间：2-4 小时。处理完成后我们会通过邮件通知您。
请您耐心等待，感谢您的理解。
```

#### 少样本示例的设计原则
- **示例要真实**：用实际运行中遇到的典型案例，不要编造
- **示例要覆盖边界**：包括“正常流程”和“异常/边界情况”
- **示例要展示推理过程**：不只是最终答案，要展示完整的思考-行动-观察过程
- **不要太多**：2-3 个就够了，太多会占用上下文且边际收益递减
- **放在 Prompt 的哪个位置**：通常放在详细指令之后、关键提醒之前；长 Prompt 中可以在相关部分重复引用

### 四、ReAct Prompt 的结构化思考引导

ReAct 模式的核心是“思考-行动-观察”循环，但很多 Agent 的思考是混乱的——没有结构、跳步、重复。结构化思考引导可以显著提升推理质量。

#### 结构化思考模板
```
每次思考时，请按照以下结构分析：

1. 用户意图分析：
   - 用户想要什么？
   - 有什么隐含需求？

2. 当前信息评估：
   - 我已经知道什么？（从对话历史和工具结果中）
   - 我还缺少什么？

3. 行动规划：
   - 下一步需要做什么？
   - 预期结果是什么？
   - 应该调用哪个工具？参数是什么？

4. 风险判断：
   - 可能出现什么问题？
   - 如何应对？

然后根据以上分析，决定是调用工具（Action）还是给出最终答案（Final Answer）。
```

#### 为什么结构化思考有效？
- 强迫模型全面分析（不会遗漏“我还缺少什么”）
- 减少跳步（先分析再行动，不会直接跳到结论）
- 提升可解释性（思考过程有结构，方便调试）
- 减少幻觉（“当前信息评估”让模型意识到信息不足时不要瞎编）

### 五、Prompt 迭代优化方法论

#### 核心原则：从简单开始，用 traces 驱动迭代

```
迭代循环：
  1. 写一个简单的 Prompt（能跑起来就行）
       ↓
  2. 运行，收集 traces（成功案例和失败案例）
       ↓
  3. 分析失败案例，归类失败模式
       - 工具调用错误？→ 优化工具描述
       - 决策流程错误？→ 优化决策流程部分
       - 越权操作？→ 加强边界定义
       - 输出格式错误？→ 加强输出格式控制
       - 推理混乱？→ 加少样本示例或结构化思考引导
       ↓
  4. 针对失败模式优化 Prompt
       ↓
  5. A/B 测试（旧 Prompt vs 新 Prompt）
       - 用相同的测试用例集运行
       - 比较成功率、Token 成本、延迟
       ↓
  6. 如果新 Prompt 更好，采用；否则回退，重新分析
       ↓
  回到步骤 2（持续迭代）
```

#### 关键提醒
- **在有 traces 之前不要调优**——没有真实失败案例的“优化”往往是瞎猜，可能越调越差
- **一次只改一个变量**——同时改多个部分，无法判断是哪个改动起了作用（或起了反作用）
- **保留测试用例集**——每次优化后用相同的测试用例集验证，确保没有“修复了 A 但破坏了 B”
- **不要追求完美**——Prompt 优化是无止境的，达到可接受的成功率就可以上线，持续迭代

### 六、Agent Prompt vs 普通 LLM Prompt

| 维度 | 普通 LLM Prompt | Agent System Prompt |
|------|----------------|-------------------|
| 指导范围 | 一次回答 | 几十轮对话、多次工具调用 |
| 核心内容 | 任务描述、输出要求 | 身份、边界、决策流程、工具指南、错误处理 |
| 长度 | 通常较短（几十到几百字） | 通常较长（几百到几千字） |
| 迭代方式 | 基于单次输出质量 | 基于完整运行轨迹（traces） |
| 失败模式 | 回答不准确、格式错误 | 工具调用错误、越权、死循环、决策混乱 |
| 少样本 | 可选，通常 1 个就够 | 推荐，2-3 个展示完整推理流程 |
| 边界定义 | 不太重要（单次任务） | 至关重要（自主运行可能越权） |
| 错误处理 | 通常不需要 | 必须包含（工具失败、信息不足等） |

### 七、实证对照与升级路径：从 prompts.chat 社区 Prompt 到 Agent System Prompt

[f/prompts.chat](https://github.com/f/prompts.chat)（原名 Awesome ChatGPT Prompts，2022 年 12 月上线，GitHub 143k+ stars）是最早、规模最大的开源 Prompt 库之一，配套官方书稿《The Art of ChatGPT Prompting》。其 `prompts.csv` 收录 2,471 条社区 Prompt（TEXT 2,123 / STRUCTURED 327 / IMAGE 21；长度中位数约 1,000 字符）。下面从语料中提炼反复出现的句式机制，再给每个模式一条“升级到 Agent 场景”的路径。

统计口径说明：占比为对全量 2,471 条逐条关键词/正则匹配的确定性计数（非抽样、非估算）。

#### 1. 语料中反复出现的六个句式机制

| 句式模式（真实例句摘录） | 占比（口径） | 底层机制 |
|------------------------|------------|---------|
| 参数化模板：`${Position:Software Developer}`、`${Mother Language:Turkish}` | 26.1%（正则匹配 `${...}`） | Prompt 即配置文件：占位符带类型化默认值，一份模板服务一类任务，是语料中占比最高的结构化模式 |
| 角色锚定：“I want you to act as a linux terminal” | 8.9%（act 列以 Act as 开头，或 Prompt 以 I want you to act as 开头） | 用职业/实体的词表先验收窄输出分布——模型“进入角色”后，术语、语气、行为都被角色约束 |
| 首轮初始化：“my first command is pwd” | 5.8%（含 my first 字样） | 消除冷启动歧义：立刻给一条真实输入，强制模型产出第一轮示范输出，避免空转确认 |
| 输出钉死：“only reply with the terminal output inside one unique code block, and nothing else” | 1.1%（含 only reply/answer） | 封堵模型自带的“解释欲”，把输出空间压到单一格式，让下游可以程序化解析 |
| 通道隔离：“when I need to tell you something in English, I will put text inside curly brackets {like this}” | 0.7%（含 curly brackets/braces 句式） | 控制流与数据流分离：自然指令走 Prompt 通道，用户数据走花括号通道——prompt injection 防御的雏形 |
| 交互节流：“Ask me the questions one by one and wait for my answers” | 0.1%（含 wait for my answers） | 显式禁止一次性倾倒，强制回合制，把“什么时候停”写进 Prompt |

#### 2. 六个模式的 Agent 场景升级路径

单轮 Prompt 的机制拿到 Agent 场景大多要“升维”——因为 Agent 多轮、自主、动真格（真实调用工具）。升级方向基本都落在九段式的对应段上：

| 社区句式（单轮版） | Agent 升级版（System Prompt / 架构做法） | 对应九段式 |
|------------------|--------------------------------------|-----------|
| 角色锚定 | 角色不只写专长，还要写权限上限：能做什么、DO NOT 边界（单轮 Prompt 不怕越权，Agent 每一步都在动真格） | ① 身份 + ③ 边界 |
| 输出钉死（文字约束） | 改用 Function Calling 的 JSON Schema 结构化输出，由 harness 程序化解析，不靠模型自觉守格式（语料 type 列 STRUCTURED 327 条是社区在这方向的实践） | ⑥ 输出格式 |
| 通道隔离（花括号） | 上升为注入防御原则：工具返回值、网页内容一律视为数据而非指令，harness 层做隔离转义 | ⑦ 质量标准 + 架构层 |
| 交互节流 | 上升为 HITL 闸门：harness 可暂停等用户确认再继续，System Prompt 写清“何时必须停下询问” | ⑤ 决策指南 |
| 首轮初始化 | 上升为状态初始化 + golden path：System Prompt 给第一步动作或一条示例轨迹（少样本），把冷启动变成确定行为 | 少样本三件套 |
| 参数化模板 | 上升为 context engineering：占位符注入的是运行时状态（用户目标、已收集信息），由 harness 在每轮组装 | 上下文组装（harness 层） |

#### 3. 书稿的两个机制级观点（直接补本文盲区）

- **Loop engineering（书稿第 14 章）**：“Context engineering 决定模型能看见什么，loop engineering 决定系统下一步做什么。” 循环五动作 Frame → Act → Observe → Evaluate → Adapt，且“**工程量不在箭头上，而在箭头之间的契约里**”：什么算一次有效动作、哪些观察可信、按什么标准评估（对照显式标准，不是模型的自信）、状态留什么、何时停（stop rule + 预算）。**推断**：本文九段式的⑤决策指南和⑧错误处理，本质上是在 System Prompt 里预写 loop 的契约——决策指南 = Frame/Evaluate 的规则化，错误处理 = Adapt 的规则化；而 stop rule 和预算通常不在 Prompt 里，在 harness 里。
- **Harness（书稿第 26 章）**：书稿把 Model / Harness / Agent / Prompt / Skill / Tool 六分开，并强调“在回复里写‘运行测试’什么都不会发生——必须有真工具执行命令并把结果带回来”。harness 负责准备上下文、暴露工具、校验工具调用、检查权限、限额、可在需要时暂停等用户输入。**事实**：这印证本文三.二工具描述的机制——工具描述是写给模型看的“使用说明书”，而执行、鉴权、重试、限额都发生在 harness 层，System Prompt 只能描述行为，不能执行行为。

另一个可借用的框架：书稿第 2 章把有效 Prompt 拆成六块积木——**Role、Context、Task、Constraints、Format、Example**（“不是每条 Prompt 都需要全部积木”），与九段式同构：Role↔①身份、Constraints↔③边界、Format↔⑥格式、Example↔少样本；差异在 Agent 特有的④工具指南、⑤决策流程、⑧错误处理。书稿第 25 章给层级类比：“**Prompt 是原子 → Skill 是分子 → Agent 是完整结构**”，与本文“普通 Prompt / Agent System Prompt”的二分一致。

对照结论（**推断**，非语料方官方结论）：

1. 社区经典 Prompt 的典型形态是“角色锚定 + 单次任务 + 输出钉死 + 首轮初始化”，属普通 LLM Prompt；Agent 特有的错误处理（约 4%）与工具调用协议在语料中明显缺位，与本文第一节论断互证。
2. 把 prompts.chat 式人设 Prompt 直接当自主 Agent 的 System Prompt 是常见误区——它没有 DO NOT 边界、没有错误处理、没有工具指南，按坑 2 的模式必然越权。
3. 语料六模式不白学：每个单轮模式都有明确的 Agent 升级路径（上表），从社区 2,471 条实践到 Agent 宪法，差的不是“写得更多”，而是把单轮技巧交给 harness、把长期契约留给 System Prompt。

你的核心目标是：快速、准确地解决用户的技术问题，让用户满意。
如果问题超出你的能力范围，及时升级给人工工程师。

# 能力与边界

## 你可以做（DO）：
- 查询公司知识库，获取产品使用指南和故障排查方案
- 查询用户的订单状态和产品信息
- 创建技术支持工单，升级给人工工程师
- 指导用户进行常见操作（如重置密码、更新版本、配置设置）

- ⚠️ 泄露其他用户的个人信息或订单信息
- ⚠️ 承诺任何形式的退款、赔偿或折扣（这超出了你的权限）
- ⚠️ 修改用户的账户设置或个人信息（只能指导用户自己操作）
- ⚠️ 编造知识库中不存在的解决方案（不确定时要承认并升级）
- ⚠️ 讨论政治、宗教等与技术支持无关的话题

# 可用工具

1. search_knowledge_base(query, category)
   - 用途：当用户提出技术问题、产品使用问题或故障排查问题时，搜索知识库
   - 参数：
     - query: 搜索关键词，应该是具体的技术术语或问题描述
     - category: 问题分类，可选值：technical（技术问题）、product（产品使用）、billing（账单相关）
   - 不要用于：查询订单状态、用户个人信息

2. query_order(order_id)
   - 用途：当用户询问订单状态、发货信息、产品版本时使用
   - 参数：
     - order_id: 订单编号，用户通常会提供；如果用户没提供，先询问
   - 不要用于：查询技术问题的解决方案

3. create_ticket(title, description, priority)
   - 用途：当问题无法在知识库中找到答案，或需要人工工程师处理时，创建工单
   - 参数：
     - title: 工单标题，简要描述问题
     - description: 详细描述，包括用户的问题、已尝试的解决方案、相关信息
     - priority: 优先级，可选值：low（一般问题）、medium（影响使用）、high（完全无法使用）
   - 不要用于：知识库中已有明确答案的问题

# 决策流程

每次收到用户消息时，请按照以下流程处理：

1. **理解问题**：分析用户的问题是什么，属于哪个类别
2. **判断是否需要查询信息**：
   - 如果是技术问题且你不确定答案 → 调用 search_knowledge_base
   - 如果是订单相关问题 → 调用 query_order（需要 order_id 时先询问用户）
   - 如果你已经知道答案 → 直接回答
3. **判断是否能解决**：
   - 知识库中有明确答案 → 按照答案指导用户
   - 知识库中没有答案，或问题复杂 → 创建工单（create_ticket）并告知用户
4. **给出回复**：清晰、准确、友好地回复用户
5. **确认满意度**：询问用户问题是否解决，是否还需要其他帮助

# 输出格式

## 思考格式（内部推理，不对用户展示）：
Thought: [按照"用户意图分析→当前信息评估→行动规划→风险判断"的结构思考]

## 行动格式（调用工具时）：
Action: [工具名](参数名=参数值)

## 最终答案格式（给用户的回复）：
Final Answer:
[清晰、有条理的回复。技术问题要给出具体步骤。]

如果创建了工单，请在回复中包含工单号和预计处理时间。

# 质量标准

- **准确性**：所有技术信息必须来自知识库，不能编造
- **具体性**：技术指导要给出可执行的具体步骤，不要只说"请检查设置"
- **及时性**：尽量在最少的轮次内解决问题，不要让用户反复提供信息
- **友好性**：语气要专业、友好、有同理心，特别是用户遇到问题时
- **诚实性**：不知道就说不知道，不要瞎猜；不确定时要承认并升级

# 错误处理

- **工具调用失败**：重试一次。如果仍然失败，告知用户"系统暂时不可用，请稍后再试"，并记录问题

### ReAct 循环 + 结构化思考的 Agent

```python
# client/MODEL 沿用上节（env 三件套见上节说明）
from openai import OpenAI
import json

client = OpenAI()

REACT_PROMPT = """
你是一个研究 Agent，可以使用搜索工具获取信息。

# 思考结构
每次思考时，请按照以下结构分析：
1. 用户意图：用户想要什么？
2. 已有信息：我已经知道什么？
3. 缺失信息：我还需要知道什么？
4. 下一步：我应该做什么？（搜索 / 回答）

# 行动规则
- 如果信息不足，调用 search 工具获取更多信息
- 如果信息足够，直接给出最终答案
- 不要重复搜索相同的内容
- 最多搜索 3 次，超过后基于已有信息回答

# 输出格式
Thought: [你的结构化思考]
Action: search(query="搜索关键词")
或
Final Answer: [你的最终答案]
"""

def search_tool(query: str) -> str:
    """模拟搜索工具"""
    return f"搜索结果：关于'{query}'的相关信息..."

def run_react_agent(user_query: str, max_steps: int = 5) -> str:
    """运行 ReAct Agent"""
    messages = [
        {"role": "system", "content": REACT_PROMPT},
        {"role": "user", "content": user_query}
    ]

    for step in range(max_steps):
        print(f"\n--- 步骤 {step + 1} ---")

        # LLM 推理
        response = client.chat.completions.create(
            model=MODEL,
            messages=messages
        )
        assistant_message = response.choices[0].message
        messages.append(assistant_message)
        print(f"Agent: {assistant_message.content}")

        # 判断是否是最终答案
        if "Final Answer:" in assistant_message.content:
            final_answer = assistant_message.content.split("Final Answer:")[-1].strip()
            print(f"\n最终答案：{final_answer}")
            return final_answer

        # 判断是否需要调用工具
        if "Action:" in assistant_message.content:
            # 解析工具调用
            action_part = assistant_message.content.split("Action:")[-1].strip()
            if action_part.startswith("search"):
                # 提取 query 参数
                import re
                match = re.search(r'query="([^"]+)"', action_part)
                if match:
                    query = match.group(1)
                    print(f"调用搜索工具：{query}")
                    result = search_tool(query)
                    # 工具结果作为 user 消息加入
                    messages.append({"role": "user", "content": f"Observation: {result}"})
                    continue

        # 没有明确的 Action 或 Final Answer，提示 Agent
        messages.append({"role": "user", "content": "请按照格式输出：Thought + Action（调用工具）或 Final Answer（最终答案）"})

    return "达到最大步骤数，未能完成任务"

# 使用
result = run_react_agent("人工智能的发展历史是什么？")
```

## 五、易混概念对比表

| 维度 | 普通 LLM Prompt | Agent System Prompt |
|------|----------------|-------------------|
| 指导范围 | 一次回答 | 几十轮对话+多次工具调用 |
| 核心内容 | 任务描述、输出要求 | 身份、边界、决策流程、工具指南、错误处理 |
| 长度 | 几十到几百字 | 几百到几千字 |
| 迭代依据 | 单次输出质量 | 完整运行轨迹（traces） |
| 主要失败模式 | 回答不准确、格式错误 | 工具调用错误、越权、死循环、决策混乱 |
| 边界定义 | 不太重要 | 至关重要 |
| 错误处理 | 通常不需要 | 必须包含 |
| 少样本 | 可选，1个就够 | 推荐，2-3个展示完整流程 |

| Prompt 组成部分 | 重要性 | 说明 |
|---------------|--------|------|
| 边界定义（DO/DO NOT） | ⭐⭐⭐⭐⭐ | 自主 Agent 最容易越权 |
| 决策流程 | ⭐⭐⭐⭐⭐ | Agent 不知道流程时会混乱 |
| 工具使用指南 | ⭐⭐⭐⭐⭐ | 工具调用错误是最常见失败 |
| 输出格式 | ⭐⭐⭐⭐ | 格式不稳定导致解析失败 |
| 身份和目标 | ⭐⭐⭐ | 设定基调 |
| 质量标准 | ⭐⭐⭐ | 提升输出质量 |
| 错误处理 | ⭐⭐⭐ | 减少失败影响 |
| 少样本示例 | ⭐⭐⭐ | 对复杂推理有效 |
| 关键提醒 | ⭐⭐ | 长 Prompt 中重复强调 |

| 工具描述要素 | 说明 | 缺失后果 |
|------------|------|---------|
| 清晰的名称 | 具体描述功能 | 模型不知道工具是做什么的 |
| 使用时机 | 什么时候用+什么时候不用 | 模型无法判断是否该调用 |
| 参数描述 | 类型+含义+示例 | 模型不知道传什么格式 |
| 枚举限制 | 限定可选值 | 模型传入无效值 |
| 必填字段 | 明确哪些参数必须传 | 模型遗漏必要参数 |

| 少样本示例数量 | 效果 | 上下文成本 |
|-------------|------|-----------|
| 0 个 | 基线，复杂推理可能混乱 | 最低 |
| 1 个 | 显著提升 | 低 |
| 2-3 个 | 最佳平衡点 | 中 |
| >5 个 | 边际收益递减，可能过拟合 | 高 |

| 迭代阶段 | 动作 | 产出 |
|---------|------|------|
| 初始 | 写简单 Prompt，能跑起来 | v1 Prompt |
| 收集 | 运行，收集 traces（成功+失败） | 失败案例库 |
| 分析 | 归类失败模式 | 失败模式分类 |
| 优化 | 针对失败模式修改 Prompt | v2 Prompt |
| 验证 | A/B 测试（v1 vs v2） | 测试报告 |
| 决策 | 采用更好的版本，或回退重新分析 | 最终版本 |

## 六、3个实战中的常见坑

### 坑 1：System Prompt 写得太长太复杂，模型忽略了关键规则

**现象**：团队写了一个 3000 字的“完美” System Prompt，包含了所有能想到的规则、流程、示例。但运行时发现 Agent 仍然犯各种错误——越权操作、不按流程走、忽略边界定义。分析 traces 发现，模型似乎“忘记”了 Prompt 中前面的规则，只遵循了最后面的几条。

#### 避坑
- **Prompt 不是越长越好**：模型的注意力是有限的，Prompt 越长，中间的规则越容易被忽略（“中间遗忘”现象，出处：Liu et al. 2023《Lost in the Middle》，实测于长上下文信息位置；迁移到 System Prompt 遵循度属推断，且新一代模型已部分缓解）。常见的“生产级控制在 1000-2000 字”说法没有可靠来源（存疑），可靠的原则是：精简、重点突出
- **关键规则放在开头和结尾**：模型对开头和结尾的内容注意力最高。把最重要的规则（如安全边界、核心流程）放在开头，然后在结尾用“关键提醒”重复强调
  ```
  开头：⚠️ 最高优先级规则：绝对不能泄露用户信息！绝对不能承诺退款！
  ...（中间是详细规则）...
  结尾：⚠️ 再次提醒：绝对不能泄露用户信息！绝对不能承诺退款！
  ```
- **用结构化标记突出重要内容**：用 `⚠️`、`# 最高优先级`、`**加粗**` 等标记让重要规则在视觉上突出。模型对结构化标记的内容注意力更高
- **把规则分组，用标题分隔**：不要把所有规则混在一起，用清晰的标题分组（如“# 边界定义”、“# 决策流程”、“# 工具使用”）。模型更容易找到和遵循有组织的内容
- **定期“精简”Prompt**：每过一段时间，回顾 Prompt，删除不再需要的规则、合并重复的规则、简化过于复杂的描述。Prompt 会随着迭代越来越长，需要主动维护
- **用少样本示例替代冗长描述**：对于复杂的行为模式，一个好的少样本示例比 500 字的描述更有效。示例展示了“具体怎么做”，而描述只是“应该怎么做”
- **类比**：就像员工手册——一本 500 页的手册，员工不会读完，更不会记住所有规则。一本 50 页的精简手册，重点突出，员工反而能记住关键规则。System Prompt 也是一样，“少即是多”

### 坑 2：只定义了“应该做什么”（DO），没有定义“不能做什么”（DO NOT），导致 Agent 越权

**现象**：团队给 Agent 写了详细的职责描述和工作流程，但没有明确的边界定义。运行后发现：①Agent 在用户要求时“帮忙”修改了用户的账户设置（越权操作）；②Agent 对不满意的用户“承诺”了退款（超出权限）；③Agent 在回答技术问题时“编造”了知识库中不存在的解决方案（幻觉）。这些越权行为导致了用户投诉和安全风险。

#### 避坑
- **DO 和 DO NOT 同样重要**：对于自主运行的 Agent，定义“不能做什么”和定义“应该做什么”同样重要。Agent 倾向于“尽力帮助用户”，如果没有明确的边界，它会尝试做任何用户要求的事——包括越权操作
- **明确列出最高优先级的禁止事项**：在 Prompt 开头和结尾用 `⚠️` 标记最高优先级的禁止规则，如：
  ```
  ⚠️ 绝对不能泄露其他用户的个人信息！
  ⚠️ 绝对不能承诺任何形式的退款、赔偿或折扣！
  ⚠️ 绝对不能修改用户的账户设置或个人信息！
  ⚠️ 绝对不能编造知识库中不存在的解决方案！
  ```
- **用场景化的 DO NOT**：不要只说“不要越权”，要具体到场景：
  - ❌ 不好：“不要做超出你权限的事”
  - ✅ 好：“当用户要求退款时，不要直接同意，要告知用户退款需要人工审核，并创建工单”
- **给越权场景提供替代方案**：不要只说“不能做”，还要说“应该怎么做”：
  - “当用户要求修改账户设置时，不要直接修改，要指导用户自己在设置页面操作，或创建工单让人工协助”
- **在工具层面也加限制**：Prompt 是“软约束”，工具权限是“硬约束”。即使 Prompt 说不能修改账户设置，如果工具有修改账户的能力，Agent 仍可能调用。要在工具注册层面限制 Agent 能调用的工具（只给它需要的工具，不给越权工具）
- **监控越权行为**：在日志中记录 Agent 的所有工具调用和输出，定期检查是否有越权行为。发现越权后，及时加强 Prompt 中的边界定义
- **类比**：就像新员工入职——只告诉他“你要尽力帮助客户”是不够的，还要明确告诉他“你不能给客户打折、不能修改客户账户、不能承诺退款”。如果不明确边界，热心的新员工可能会为了让客户满意而做出越权的事。Agent 也是一样，它“想帮助用户”，但需要明确的边界来防止越权

### 坑 3：在没有真实失败案例（traces）的情况下“优化” Prompt，越调越差

**现象**：团队写完第一版 Prompt 后，没有充分测试就开始“优化”——根据“感觉”加规则、加示例、改描述。改了几版后发现，Agent 的表现反而越来越差：原来能处理的场景现在处理不了了，新加的规则和原有的规则冲突了，Prompt 越来越长导致模型忽略了关键规则。最后不得不回退到第一版，从头开始。

#### 避坑
- **核心原则：在有 traces 之前不要调优**——没有真实失败案例的“优化”是瞎猜。你以为某个规则会改善表现，但实际上可能和其他规则冲突，或者模型根本不遵循。先让 Prompt 跑起来，收集至少 20-50 个真实案例（包括成功和失败），再开始优化
- **建立测试用例集**：在优化之前，先建立一个固定的测试用例集（20-50 个典型场景，包括正常、边界、异常）。每次优化后，用相同的测试用例集运行，比较新旧版本的表现。没有测试用例集的“优化”是盲目的
- **一次只改一个变量**：不要同时改多个部分（如同时改边界定义、加示例、改工具描述）。一次只改一个变量，运行测试，确认这个改动是正面的还是负面的，再决定是否保留。同时改多个变量，无法判断是哪个改动起了作用（或起了反作用）
- **分析失败案例，归类失败模式**：不要看到失败就“加规则”。先分析失败案例，归类失败模式：
  - 是工具调用错误？→ 优化工具描述
  - 是决策流程错误？→ 优化决策流程部分
  - 是越权操作？→ 加强边界定义
  - 是输出格式错误？→ 加强输出格式控制
  - 是推理混乱？→ 加少样本示例或结构化思考引导
  针对具体的失败模式优化，而不是“泛泛地加规则”
- **A/B 测试**：对于重要的改动，用 A/B 测试验证——一半流量用旧 Prompt，一半用新 Prompt，比较真实用户场景下的表现。实验室测试用例集可能覆盖不全，A/B 测试能发现真实场景中的问题
- **保留版本历史**：每次优化都保留版本（v1, v2, v3...），记录改动内容和测试结果。如果新版本更差，可以快速回退到上一个好版本。不要“覆盖式”修改，丢失了历史版本
- **接受“足够好”**：Prompt 优化是无止境的——你永远可以再优化一点。但当成功率达到可接受的水平（如 90%+），就应该上线，在真实使用中持续迭代。不要追求“完美”而迟迟不上线
- **类比**：就像产品迭代——没有用户反馈就“拍脑袋”加功能，往往会把产品搞砸。正确的做法是：先上线 MVP（最小可行产品），收集用户反馈，分析问题，针对性地优化，A/B 测试验证。Prompt 优化也是一样，“traces 驱动的迭代”才是科学的方法

## 七、进阶问题（引导往下挖）

### 问题 1：随着推理模型（如 o1、o3）的出现，Agent 的 Prompt 工程会发生什么变化？“显式 Prompt 工程”会被“隐式推理”取代吗？

#### 引导思考
- **传统模型（GPT-4o 等）的 Prompt 工程**：
  - 需要显式指导推理过程（如 ReAct 的“思考→行动→观察”格式）
  - 需要结构化思考引导（“按照以下结构分析：1.用户意图 2.已有信息...”）
  - 需要少样本示例展示复杂推理模式
  - 需要详细的决策流程描述
  - 本质：模型“不会”复杂推理，需要 Prompt “教”它怎么做
- **推理模型（o1、o3 等）的特点**：
  - 内置了隐式推理能力（模型内部会进行多步推理，不需要显式指导）
  - 推理过程是“隐式”的（不展示思考过程，直接给出答案）
  - 对复杂问题的推理能力更强（数学、逻辑、规划）
  - 对 Prompt 的依赖降低（简单的 Prompt 也能得到好的结果）
- **推理模型时代的 Prompt 工程变化**：
  - **不需要显式指导推理格式**：不需要写“按照 Thought→Action→Observation 的格式输出”，推理模型会自己进行多步推理
  - **不需要结构化思考引导**：不需要“按照以下结构分析”，推理模型会自己组织推理过程
  - **少样本示例的重要性降低**：推理模型本身就有很强的推理能力，不需要示例“教”它怎么推理
  - **边界定义和安全约束更重要**：推理模型能力更强，可能做更复杂的事，也可能造成更大的危害。明确的边界定义（DO/DO NOT）比推理指导更重要
  - **目标和约束的描述更重要**：不需要教“怎么做”，但需要明确“做什么”和“不能做什么”。推理模型会自己想“怎么做”，但需要你告诉它目标和边界
  - **工具描述仍然重要**：即使是推理模型，也需要准确的工具描述来判断“什么时候调用哪个工具”
  - **输出格式控制仍然重要**：推理模型的输出可能更自由，需要明确的格式约束来确保下游能解析
- **“显式 Prompt 工程”会被取代吗？**
  - **不会完全取代，但重心会转移**：
    - 从“教模型怎么推理”（显式推理指导）→ 转移到“明确目标和边界”（约束定义）
    - 从“详细的流程描述”→ 转移到“清晰的目标和评估标准”
    - 从“少样本示例”→ 转移到“边界案例和安全约束”
  - **推理模型不是万能的**：
    - 推理模型仍然会犯错（幻觉、逻辑错误）
    - 推理模型的隐式推理不可控（不知道它内部是怎么推理的）
    - 对于特定领域的流程（如公司的特定工作流程），仍然需要 Prompt 明确描述
    - 对于高风险场景，显式的推理过程（可审计）比隐式推理（黑盒）更安全
- **混合模式：显式 + 隐式**
  - 很多生产级系统会用混合模式：
    - 用推理模型做复杂推理（隐式）
    - 用 Prompt 明确目标、边界、工具、输出格式（显式约束）
    - 用外部验证（工具调用结果、人工审核）确保推理结果正确
  - 就像“聪明的员工 + 明确的岗位说明书”——员工很聪明（推理模型），自己会想办法解决问题，但仍然需要岗位说明书明确职责、边界、流程和质量标准
- **类比**：就像从“手工计算器”到“智能手机”的演进——
  - 手工计算器（传统模型）：你需要明确告诉它每一步怎么算（显式指导）
  - 智能手机（推理模型）：你只需要说“帮我算一下这个月的预算”，它自己会想办法（隐式推理）
  - 但即使是智能手机，你仍然需要明确“预算的规则是什么”（目标和约束）、“哪些支出不能算”（边界）、“输出什么格式”（格式要求）。Prompt 工程的重心从“怎么算”转移到了“算什么和不能算什么”
- 延伸：后续知识点（生产级 Agent 架构设计、评估与生产）会深入讲解推理模型时代的 Agent 设计和验证策略

### 问题 2：Agent 的 Prompt 优化和传统软件的“代码调试”有什么异同？能不能用“自动化 Prompt 优化”（如 APE、DSPy）替代人工 Prompt 工程？

#### 引导思考
- **相同点**：
  - **都是“迭代优化”**：写第一版→测试→发现问题→修改→再测试。和代码调试的“写代码→运行→发现 bug→修复→再运行”一样
  - **都需要“复现问题”**：发现失败案例后，需要能稳定复现，才能验证修复是否有效。和代码调试的“复现 bug”一样
  - **都需要“回归测试”**：修复一个问题后，要确保没有破坏其他功能。和代码调试的“回归测试”一样
  - **都需要“版本管理”**：保留历史版本，出问题可以回退。和代码的 Git 版本管理一样
  - **都需要“日志和监控”**：记录运行时行为，发现异常。和代码的日志监控一样
- **不同点**：
  - **确定性 vs 概率性**：
    - 代码：确定性的——相同的输入一定得到相同的输出（除非有随机数或并发）
    - Prompt：概率性的——相同的输入可能得到不同的输出（LLM 的随机性）。同一个 Prompt 这次成功，下次可能失败
    - 影响：Prompt 优化需要更多的测试样本（统计意义上的改进），不能只靠一两个案例
  - **可解释性**：
    - 代码：可以用断点、单步调试，精确看到每一步发生了什么
    - Prompt：LLM 的内部推理是黑盒，只能看到输入输出，无法精确知道“为什么模型这么做”
    - 影响：Prompt 优化更多是“假设-验证”（猜测失败原因→修改→验证），而不是“精确诊断”
  - **修改的影响范围**：
    - 代码：修改一个函数，影响范围通常是可预测的（调用这个函数的地方）
    - Prompt：修改一句话，可能影响模型的整体行为（因为模型是“整体理解”Prompt 的）。改了 A 规则，可能意外影响了 B 行为
    - 影响：Prompt 优化需要更全面的回归测试，一次只改一个变量
  - **优化目标**：
    - 代码：通常是明确的（功能正确、性能达标、无 bug）
    - Prompt：优化目标可能是模糊的（“回答更好”、“更智能”），需要量化为具体指标（成功率、准确率、用户满意度）
- **自动化 Prompt 优化（APE、DSPy 等）**：
  - **APE（Automatic Prompt Engineer）**：自动生成和筛选 Prompt 的方法。用 LLM 生成候选 Prompt，在测试集上评估，选择最好的。类似于“遗传算法”——生成→评估→选择→变异→再评估
  - **DSPy（Declarative Self-improving Language modules）**：把 Prompt 优化变成“编译优化”——你声明“我要什么”（输入输出示例、评估指标），DSPy 自动优化 Prompt（和模型参数）来达到目标。类似于编译器的“优化器”——你写高级代码，编译器自动优化成高效的机器码
  - **自动化优化的优势**：
    - 速度快：可以在短时间内尝试几百上千个 Prompt 变体
    - 不依赖经验：不需要“Prompt 工程专家”的直觉
    - 可复现：优化过程是自动化的、可复现的
    - 可以优化复杂目标：如“在成本限制内最大化准确率”
  - **自动化优化的局限**：
    - 需要好的评估指标：如果评估指标不准确（如“回答质量”难以自动评估），自动化优化会“优化到错误的目标”
    - 需要大量测试数据：自动化优化需要大量的测试用例来评估，数据不足会过拟合
    - 可能产生“不可读”的 Prompt：自动优化出的 Prompt 可能对人类来说不可理解（类似于编译器优化出的机器码），难以人工调试和维护
    - 边界和安全约束难以自动优化：安全边界、伦理约束等“软约束”难以用评估指标量化，需要人工设计
    - 泛化能力：在测试集上优化得好，不代表在真实场景中也好（过拟合）
- **未来趋势：人工 + 自动化混合**
  - **人工负责“设计”**：定义目标、边界、评估指标、测试用例、安全约束
  - **自动化负责“优化”**：在人工定义的框架内，自动搜索最优的 Prompt 变体
  - **类似于“软件开发”的演进**：
    - 早期：程序员手写汇编（人工写 Prompt）
    - 后来：编译器自动优化（自动化 Prompt 优化）
    - 现在：程序员写高级代码，编译器优化，但程序员仍然需要设计架构、定义接口、写测试（人工定义框架，自动化优化细节）
  - Prompt 工程也会遵循同样的路径：从“手工 craft”到“声明式 + 自动优化”，但人工的“架构设计”和“边界定义”仍然不可替代
- **类比**：就像“汽车设计”的演进——
  - 早期：汽车设计师手工画每一个零件（人工写 Prompt）
  - 后来：CAD 软件自动生成和优化零件形状（自动化 Prompt 优化）
  - 现在：设计师定义设计目标（速度、安全、成本）和约束（法规、材料限制），软件自动优化细节，但设计师仍然需要做关键决策（整体架构、安全标准、品牌调性）
  - Prompt 工程也是一样，自动化工具会越来越强，但“定义目标和边界”的人工判断仍然是核心
- 延伸：后续知识点（Agent 评估指标、生产级 Agent 架构设计）会深入讲解如何建立评估体系和自动化优化流程

## 八、四关自测

### 复述关（3句话讲清）
1. Agent 的 Prompt 工程和普通 LLM Prompt 有本质区别——普通 Prompt 只指导“一次回答”，Agent 的 System Prompt 是指导“几十轮对话+多次工具调用+错误恢复”的行为宪法，是控制 Agent 行为的最强大杠杆。
2. 一个生产级 System Prompt 要回答九个问题：身份、目标、能力边界（DO/DO NOT）、可用工具、输出格式、决策流程、质量标准、错误处理、关键提醒；其中边界定义（特别是 DO NOT）和工具使用指南最容易出问题。
3. 核心方法论是“从简单开始、用 traces 驱动迭代”——没有真实失败案例的“优化”是瞎猜，必须先跑起来收集 traces、按失败模式归类优化、一次只改一个变量、A/B 测试验证。

### 举例关（真实场景）
你做一个电商客服 Agent：用户说“给我退款”，你没写 DO NOT 边界，Agent 为了“让用户满意”直接调用退款工具承诺全额退款——越权了。正确做法是在 System Prompt 开头结尾用 ⚠️ 标出“绝对不能承诺退款，退款必须创建工单转人工审核”，并在工具层面根本不给它退款工具。这就是“软约束（Prompt）+ 硬约束（工具权限）”双保险。

### 反例关（边界条件）
写一个 3000 字的“完美”System Prompt，把所有能想到的规则全塞进去，结果模型出现“中间遗忘”——只遵循了开头和结尾的几条，中间的规则全忽略了，越权、不按流程走照旧发生。Prompt 不是越长越好，字数上限没有可靠来源（存疑），以精简为准，关键规则放开头结尾用 ⚠️ 重复强调。另外，没有 traces 就凭“感觉”加规则，越调越差、新旧规则冲突。

### 教学关（给小白讲）
Agent 的 System Prompt 就像给新员工的入职手册：告诉他是谁、该干啥、能用什么工具、什么绝对不能干、遇到问题找谁、回复要啥格式。手册越清楚，新员工越能独立干活不闯祸；手册含糊或太厚记不住，他就会瞎干——比如为了讨好客户擅自答应退款。所以手册要精简、重点（红线）放最前面和最后面反复叮嘱，还要先让他真干一段时间、看他在哪摔倒了，再针对性地补手册，不能拍脑袋瞎改。
