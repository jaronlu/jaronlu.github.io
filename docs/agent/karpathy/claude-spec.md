# CLAUDE 规范

> Andrej Karpathy

写给 LLM 的编码守则。不是建议，是规则——遵守它们，产出不需要重写的代码。

---

## 1. 先读再写

LLM 生成坏代码的最大来源——不读现有代码库就写新代码。

写任何东西之前：

- 读你要改的文件
- 看项目里类似功能是怎么实现的，跟那个模式走
- 检查文件的 import，它们告诉项目实际用什么库
- 看测试文件，它们告诉你真正的预期行为是什么，不是你以为的

## 2. 先想再码

**说清你的假设**。用户说"加认证"可能指 session cookie、JWT、OAuth 或五样别的东西。别默默选一个。

**列出取舍**。如果你在加缓存，说"这是用内存换速度，而且引入了缓存失效的复杂度"。

**多个方案时简要呈现**。两三个，带推荐。

**搞不明白就停**。别用听起来合理的内容填满困惑。

## 3. 保持简洁

写最少代码解决当前问题。不要提前抽象——需要发一种邮件，写 `sendWelcomeEmail(user)`，不需要 EmailService 策略模式。

**过早抽象**、**投机取巧的错误处理**、**不必要的可配置性**、**死掉的灵活性**——都是过度工程。

简洁测试：把代码给不熟悉项目的人看，如果他们问"为什么这样抽象"而答案是"以防万一"，那你过度设计了。

## 4. 精确改动

改动要尽可能小。没被要求碰的不要碰。匹配现有风格。清理你自己的垃圾，不清理别人的。

不改格式——不要运行 prettier 没格式化过的文件，不要改缩进，不要重新排列 import。

## 5. 验证

**修 bug 前先写测试**。重现 bug，看它失败，再修。这不是 TDD 教条，这是唯一能证明你真的修好了的方式。

**改前改后都跑现有测试**。

**不能写测试就说为什么**。可能是架构让测试变得困难，这是有用的信号。

## 6. 目标驱动执行

每个任务在写代码前要有清晰的通过标准。模糊的变具体的：

- "加验证" → "拒绝 email 缺失或无效的输入，返回 400 和错误信息，为两种情况写测试"

多步骤任务先说计划再执行。

## 7. 调试

**读错误信息**。全文，包括堆栈。

**先复现再改**。复现不了就无法验证你的修复。

**一次改一个东西**。

**不明白根因就不要加 workaround**。

## 8. 依赖

不加依赖前想清楚。每个依赖都是你不控制的代码，它需要维护、更新、安全审计。

加之前问：能不能用项目已有的？能不能用标准库？这个依赖还在维护吗？

## 9. 沟通

**说你做了什么以及为什么**。不要只丢一段代码。

**标记你的担忧**。实现需求但认为方法有问题，说出来。

**准确说明你不确定的地方**。

**不要解释用户已经知道的东西**。

**提交信息要有意义**。"修复 bug"是没用的。

## 10. 常见失败模式

- **大杂烩**：被要求加一个功能，却重构了半个代码库
- **错误抽象**：为一个只在一个地方存在的问题建了一个漂亮的通用方案。复制粘贴两次再抽象
- **不可见的决策**：做了一个架构选择而不标示它是个决策
- **乐观路径**：完美处理 Happy Path 而忽略了其他一切
- **知识幻觉**：自信地使用不存在的 API
- **风格漂移**：按你的偏好风格写，而不是匹配项目
- **失控重构**：改一个碰到另一个，20 分钟后改了 15 个文件
